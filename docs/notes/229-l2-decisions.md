# L2 분류·재분석 결정을 확정으로 옮겼다

## 한 일

- `docs/decisions.md` 「확정」에 `### L2` 절을 만들고 Incident 분류 방법(D-027)과 L2 재분석 기준(D-028)을 넣었다. 절 위치는 `### 에이전트`와 `### L3` 사이다.
- 「담당자가 정함」에서 두 행을 뺐다. 남은 것은 L1 판정 결과 조건(D-025), L3 실행 방식(D-030), 임베딩 모델(D-031)이다.
- 「기록」 맨 위에 한 줄을 남겼다.
- 문서 한 파일만 바뀌었다. 코드·계약·마이그레이션·설정은 건드리지 않았다.

## 계획과 달라진 점

없다.

## 다음 사람이 알아야 할 것

- **`### L2` 절은 `### L3`보다 앞에 둔다.** L3 절은 위협 시나리오 입력(D-029)을 확정하면서 #221이 만들었고 `### 저장` 바로 앞에 있었다. 단계 순서대로 읽히게 L2를 그 앞에 넣었다. L1 절이 생기면 `### 에이전트`와 `### L2` 사이가 자리다.
- **D-027의 결정 칸이 다른 행보다 길다.** 분류는 "무엇을 쓸지"가 아니라 "어떤 순서로 판단하고 실패하면 어디로 가는지"가 결정의 알맹이라 줄이면 뜻이 빠진다. 신호 등급 목록·시간 창·후보 수 같은 숫자는 설정 값이라 결정에 넣지 않고 메모에 "설정 값이다"로만 적었다.
- **확신도는 계약에 담되 판정에 쓰지 않는다.** 분류 출력에 `confidence`를 두고 Agent Log에 남기지만 거르는 데 쓰지 않는다. 임계로 거를지와 임계값은 실제 분포를 본 뒤 별도로 정한다. 지금 임계를 넣으면 근거 없는 숫자가 코드에 박힌다.
- **저장 경쟁은 고른 Incident 한 줄 잠금으로 막는다.** advisory lock은 두지 않는다. 이유는 계획 파일 "토론으로 정한 것"에 있다. 요약하면 ⑴ 에이전트 호출 뒤에 잡는 락은 경쟁 구간을 이미 지난 뒤라 막지 못하고 ⑵ 에이전트 구조(D-024)가 단계별 스레드라 L2 분류는 한 번에 하나씩 돌아 Ticket끼리의 경쟁 자체가 없다. 남는 것은 에이전트가 도는 동안 사람이 승인·종결하는 경우뿐이다.
- **이 결정은 L2-A 전체와 L2-B에 걸친다.** 개발 이슈 하나의 PR에 묻지 않고 따로 올린 이유다. L2 개발 이슈가 `/soc-plan`에서 확정 여부를 확인할 때 이 PR이 먼저 머지돼 있어야 한다.
