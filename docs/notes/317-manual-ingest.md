# 수동 수집 명령: 첫 실행 범위·겹침 구간·잠금·요약을 더해 반복 실행에 안전하게 만든다

## 한 일

- `uv run python -m soc.ingest [--since 24h]`가 조회 시작 시각을 규칙으로 정한다(D-055). 체크포인트가 없으면 `--since` 또는 `[ingest] initial_lookback_seconds`(86400)부터, 있으면 `체크포인트 − overlap_seconds`(60)부터 읽는다. `--since`가 더 이르면 그것을 쓰고, 더 늦으면 무시한다. 이전에는 체크포인트가 없으면 인덱스 전체를 가져왔다.
- `store.save_page`는 체크포인트를 저장된 `time_ms`보다 클 때만 갱신한다(같거나 작으면 `updated_at`도 그대로). `--since`로 과거를 다시 읽어도 되돌아가지 않는다.
- 수집은 `pg_try_advisory_lock`(`store.RUN_LOCK_KEY`)으로 동시에 하나만 돈다. 못 잡으면 "다른 수집이 실행 중이다"를 stderr에 쓰고 종료 코드 3으로 끝나며, ELK에 붙지 않고 아무것도 쓰지 않는다. 종료 코드는 0 성공, 1 실패한 소스·DB 오류, 2 설정·인자 오류, 3 잠금.
- 소스마다 요약 한 줄을 낸다: 구간(UTC), 가져옴, 새로 저장, 건너뜀(= 가져옴 − 새로 저장 − 격리), 격리, 페이지, 소요 초, 실패 종류와 이유. 끝에 전체 소요 시간과 "결과 확인: DB의 ingest_runs 테이블(상태 조회 명령은 아직 없다)"를 낸다. 이유 문구는 환경변수 이름·설정 키 이름만 담는다.
- 인증서 검증 실패를 실패 종류 `tls`로 나눴다(재시도하지 않는다). 인증은 `auth`, 그 밖의 연결 실패는 `network`다.

## 계획과 달라진 점

없음. 작은 선택:
- `run()`에 `since_ms`·`now_ms` 인자를 키워드로 더했다(기본값이 있어 기존 호출은 그대로다). `main()`은 `argv`를 받는다. 기본값은 빈 목록이라 pytest 인자를 읽지 않고, `python -m`은 `sys.argv[1:]`를 넘긴다.
- 빈 커서(`{}`, 0100 시기 행)는 "체크포인트 없음"으로 본다. 그래서 이 경우도 전체 조회가 아니라 기본 범위부터 읽는다.
- 가져온 건수는 저장까지 끝난 페이지의 hit 수다. 저장에 실패한 페이지의 hit는 세지 않는다.
- `tests/ingest/fake_elk.py`의 `make_settings` 기본 `overlap_seconds`는 0이다(기존 테스트의 `gte` 값을 그대로 두려고). 설정의 실제 기본값은 60이다.

## 다음 사람이 알아야 할 것

- **동작이 바뀌었다.** 체크포인트가 없는 첫 실행은 이제 최근 24시간만 가져온다. `docs/notes/264-lab-cycle.md`의 랩 절차로 처음 실행하는 환경은 더 오래된 데이터가 필요하면 `--since 30d`처럼 준다.
- **두 번째 실행의 "건너뜀"은 0이 아니다.** 겹침 구간(60초)과 `gte` 경계 때문에 이미 저장한 문서를 다시 받는다. 완료 기준은 "새로 저장 0"이다.
- **겹침 구간보다 늦게 색인된 문서는 놓친다.** 커서 필드는 아직 `@timestamp`다(#232 기록: `event.ingested` 변경은 실제 ELK에서 필드를 확인한 뒤). 이번에는 바꾸지 않았다.
- 소스가 중간에 실패해도 커밋된 페이지까지는 체크포인트가 전진한다(D-050). 이슈의 "성공한 소스만 전진"은 "실패한 페이지 뒤로는 가지 않는다"로 읽었다.
- 잠금은 세션 잠금이라 DB가 같으면 소스와 상관없이 수집 명령 하나만 돈다. 프로세스가 죽으면 연결이 끊기며 풀린다. 연결 풀러(PgBouncer 트랜잭션 모드 등)를 쓰면 세션 잠금이 맞지 않는다(지금은 쓰지 않는다).
- `errors.FAILURES`에 `tls`가 늘었다. 이를 쓰는 곳은 `ingest/`뿐이었고(`ingest_run` 계약의 `outcome`은 정규식), 마이그레이션은 없다.
- `store.save_page`의 호출자는 `run.py`뿐이다. 정규화 쪽은 영향이 없다. 저장 도중(커밋 전) 원본이 `claim_pending_batch`에 보이지 않는 것은 코드 변경 없이 db 테스트로 고정했다.
- **손으로 확인하지 못한 것(사람이 한다).** 랩 ELK에서 활성화 파이프를 띄운 채 수집을 두 번 실행해 두 번째가 새 건 0건이고 파이프가 끝까지 처리하는 것, 건수·소요 시간, Event 대상에 `event.ingested`가 있는지. 숫자는 건수로만 이 기록에 적는다(사람이 준다).

## 확인 방법

- `uv run ruff format --check .`, `uv run ruff check .` 통과.
- `uv run pytest`(1933건 통과, 종료 때 기존 `FakeSshServer` pending-task 경고가 나온다), `uv run pytest -m "db or qdrant"`(547건 통과, 로컬 PostgreSQL 17.6·Qdrant 컨테이너).
- 새 테스트: `tests/ingest/unit/test_window.py`(`--since` 읽기, 시작 시각 규칙 네 경우, 후퇴 방지, 연속 두 번 실행, 부분 실패, 요약 줄·비밀 없음, 이유 문구 구분, `tls`·`network`, 설정 검사, `--since` 오류 종료 코드 2, 잠금 종료 코드 3), `tests/ingest/db/test_manual_ingest_db.py`(체크포인트 앞으로만, 빈 커서, 과거 재조회, 연속 실행 새로 저장 0, 잠금 배타·해제, 커밋 전 원본이 정규화에 안 보임).
- 고친 기존 테스트: `test_run.py`(요약 형식), `test_quarantine_run.py`(빈 커서는 기본 범위부터).
