# 명시적으로 시작하는 ELK 수집과 RawRecord 저장 구현

## 목표

ELK의 선택된 Event와 Elastic Security Alert 원본을 RawRecord로 PostgreSQL에 보존한다. 수집기는 한 번 실행되며, 운영 환경의 cron이 주기적으로 실행한다. 각 원본 페이지와 체크포인트를 원자적으로 저장해 실패한 위치부터 다음 실행에서 재개한다.

## 방법

- 입력 대상과 필요한 조회·정렬 필드는 P01 #208에서 정한 합성 응답 및 접속 계약을 따른다. #208이 그 내용을 제공하기 전에는 해당 필드를 추측해 구현하지 않는다.
- 설정은 D-002에 따라 TOML로 읽고, URL·인증 비밀은 환경변수에서만 읽는다. SIEM 계정은 읽기 전용으로 쓴다(D-010). HTTP 요청은 확정된 클라이언트 `httpx`를 쓰고 리다이렉트를 따라가지 않는다(D-039).
- 한 번 실행하는 `soc.ingest` 명령이 Event와 Alert를 Elasticsearch 조회 API로 가져온다. 스케줄러는 만들지 않는다. 운영자가 cron에서 명령을 호출한다.
- 각 원본은 기존 RawRecord 계약에 맞춰 `id`, `kind`, `siem_profile`, ELK 문서 식별자 `<_index>/<_id>`인 `siem_ref`, `fetched_at`, 변경하지 않은 `original`로 만든다. 기존 `validate_contract`, `new_id`, 시각 변환 함수를 재사용한다.
- 체크포인트는 RawRecord와 별도인 `ingest_checkpoint` 계약과 PostgreSQL 테이블로 추가한다. 체크포인트는 SIEM 프로필, 소스 종류, 선택한 소스 키로 구분하고, 조회 재개 상태를 JSON 객체로 저장한다. 커서의 실제 필드와 의미는 #208의 조회 계약에 맞춘다.
- 페이지의 RawRecord 검증을 모두 통과하면 DB 트랜잭션 하나에서 중복되지 않은 원본을 넣고 체크포인트를 다음 페이지 위치로 갱신한다. `(siem_profile, siem_ref)`가 이미 있으면 원본을 덮어쓰지 않는다. Alert 문서는 수집 중 수정되지 않는다고 가정하며 변경 이력은 저장하지 않는다.
- 검증 또는 DB 저장이 실패하면 현재 페이지와 체크포인트 갱신을 롤백하고 해당 실행을 재시도 없이 멈춘다. 체크포인트는 마지막 성공 페이지에 남는다. 다음 cron 실행은 그 위치부터 다시 조회한다.
- 외부 입력은 데이터로만 취급한다. 원본 문서와 인증 비밀을 로그에 출력하지 않는다.

## 바꿀 곳

- `contracts/`: 별도 체크포인트 JSON Schema
- `src/soc/contracts/`: 체크포인트 계약 등록 및 생성 코드 갱신
- `src/soc/db/migrations/`: 체크포인트 테이블 마이그레이션(수집 대역)
- `src/soc/ingest/`: ELK 조회, 체크포인트를 포함한 페이지 저장, 단일 실행 진입점
- `config/default.toml`, `.env.example`: 비밀이 아닌 기본 설정과 환경변수 이름
- `tests/fixtures/ingest/`, `tests/`: 합성 Event/Alert, 페이징, 중복, 실패·재개 테스트
- `docs/notes/218-elk-rawrecord.md`: 개발 중 알게 된 점과 실행 방법

## 다른 코드와 맞물리는 곳

- 기존 `RawRecord` 계약과 `raw_records` 테이블을 재사용한다. 공통 RawRecord 필드는 바꾸지 않는다.
- 체크포인트는 새 계약·테이블이며 정규화 결과나 L1을 호출하지 않는다.
- P01 #208이 ELK 소스, 응답, 시간·정렬 필드, 권한 및 호환 범위를 확정해야 조회 커서와 외부 응답 처리를 구현할 수 있다. 이 선행 내용이 나오기 전에는 ELK 조회 로직의 구체 필드를 만들지 않는다.

## 범위 밖

- ECS/OCSF 변환, `alerts`·`events` 정규화 테이블 기록, L1 호출
- Alert의 후속 수정·상태 변경 버전 보존
- Kafka/queue push와 중계 서비스
- 애플리케이션 내장 스케줄러, 즉시 재시도·백오프
- ELK 구축, 실제/공개 데이터셋 원본, 보관 기간
- cron 자체 설치와 운영환경 배포

## 완료 기준

- [ ] P01 #208에서 정한 ELK 입력 계약에 맞는 Event·Alert 페이지를 읽어 RawRecord로 저장한다.
- [ ] cron에서 실행 가능한 단일 수집 명령이 있고, 실행 전에는 연결하지 않으며 정규화/L1과 독립적이다.
- [ ] 체크포인트 계약과 테이블이 있고, 성공한 각 페이지의 원본과 다음 위치가 한 DB 트랜잭션으로 커밋된다.
- [ ] 계약 거부, SIEM 응답 오류, DB 오류가 나면 해당 페이지가 롤백되고 체크포인트가 마지막 성공 위치를 유지하며 실행이 멈춘다.
- [ ] 다음 실행은 마지막 성공 위치에서 재개하며, 같은 `(siem_profile, siem_ref)` 원본을 중복 저장하거나 덮어쓰지 않는다.
- [ ] 손으로 만든 fixture로 두 인덱스의 같은 `_id`, 반복 페이지, 재시작, 계약 거부와 장애 동작을 검증한다.
- [ ] 비밀 값이 로그에 없고, 새 환경변수 이름만 `.env.example`에 있다.
- [ ] `uv run ruff format --check .`, `uv run ruff check .`, `uv run pytest`, `uv run pytest -m db`가 통과한다.

## 토론으로 정한 것

1. 사용자 지시에 따라 체크포인트를 별도 계약과 테이블로 #218에서 추가한다. 현재 스키마에는 체크포인트가 없고, 별도 수집 작업의 공개 계약도 확인되지 않았다. RawRecord에 운영 커서를 넣으면 원본 문서 계약과 수집 진행 상태가 섞인다.
2. Event와 Alert 모두 조회 방식으로 수집한다. Astra medium 검토 결과, Alert용 push는 지연 목표와 별도 큐/중계·복구 정책이 정해지지 않은 현재 범위에 비해 운영 계약을 늘린다.
3. 단일 실행 명령을 cron이 호출하며, 실패 시 같은 실행 안에서 재시도하지 않는다. 마지막 성공 위치를 보존해 다음 cron 실행에서 실패 페이지를 다시 처리한다. 실패 페이지를 건너뛰면 원본이 누락될 수 있다.
4. Alert 문서는 수집되는 동안 바뀌지 않는다고 가정한다. 수정 이력은 별도 계약·저장 구조가 필요하므로 후속 범위로 둔다.
5. 테스트 데이터셋은 손으로 만든 합성 fixture를 쓴다. 설계 문서에 운영용 공개 데이터셋이 없고, 보안 규칙은 공개 데이터셋 원본의 커밋을 금지한다.
6. 원본 수집만 하며 ECS/OCSF 변환을 하지 않는다. RawRecord는 ELK 응답을 변경 없이 보존하고 정규화는 별도 단계다.
7. 구현 중 P01 #208의 소스·필드·정렬 계약이 없으면 구체 조회를 임의로 정하지 않고 멈춘다. 현재 #208은 열려 있고 이 값들이 미정이다.

## 바뀐 점


### 2026-11-04 · 사람 확정(#208 방향 반영)

- 조회 대상: Alert는 space별 alias, Event는 지정한 데이터 스트림·인덱스. 대상 이름은 설정(TOML)에 두고 나중에 바꿀 수 있다. 처음 기본값은 웹·클라우드 Event 대상을 우선으로 둔다.
- 커서: 조회 시각 필드(`time_field`, 설정)의 값을 체크포인트 커서로 쓴다. 실행 안에서는 PIT와 `search_after`로 넘기고, 실행 사이에는 PIT를 이어 쓰지 않고 마지막 커밋 페이지의 시각부터 `gte`로 다시 조회한다(겹치는 문서는 `(siem_profile, siem_ref)`로 건너뛴다). 실제 Event의 시각 필드(`event.ingested` 등)는 실제 응답을 눈으로 본 뒤 설정으로 정한다.
- 실패 기록: 실패 원인을 종류 코드로 구분해 stderr와 체크포인트의 `last_error`에 남긴다. 원문과 비밀은 남기지 않는다.
- `original`은 ELK hit 객체(`_index`, `_id`, `_source` 등)를 변경 없이 저장한다.
- HTTP 클라이언트는 `docs/decisions.md` D-039의 `httpx`.

### 2026-11-04 · 리뷰 후 확인(의도 축 1번)

- 늦게 도착한 문서: `@timestamp` 커서는 색인이 늦게 끝난 문서를 놓친다. 로컬 ES에서 재현했다(0건 놓침 확인, `event.ingested` 커서는 1건 저장). Event의 커서 필드는 `event.ingested`로 바꾸는 것을 제안하며, 실제 ELK에 필드가 있는지 확인한 뒤 확정한다. 확정 전까지 기본값은 `@timestamp`다.
- 이름: Elastic 데이터 스트림 규칙 `{type}-{dataset}-{namespace}`(dataset에 하이픈 금지)와 Alert의 `.alerts-security.alerts-{space}`를 따른다. 현재 키는 이미 이 규칙에 맞아 바꾼 것은 없다.

### 2026-11-04 · 실행 이력 테이블(사람 확정)

- 체크포인트의 `last_error`를 없앤다. 체크포인트는 재개 위치(cursor)와 `updated_at`만 가진다. 이유: 같은 성공인데 hit이 있으면 `last_error`가 지워지고 0건이면 남는 불일치가 있었고, 이력이 DB에 남지 않았다.
- `ingest_runs` 테이블과 `ingest_run` 계약을 새로 둔다. 조회 대상 하나의 실행마다 한 행을 쌓는다(성공이면 `outcome = ok`, 0건 성공도 기록). 현재 상태는 대상별 가장 최근 행으로 읽는다. 실패 종류 코드는 `outcome`에 남기고 원문·비밀은 넣지 않는다.
- 마이그레이션은 적용된 `0100`을 고치지 않고 `0101`로 `last_error` 열 삭제와 `ingest_runs` 생성을 한다. 이력 기록이 실패해도 수집 결과(원본·체크포인트)에는 영향이 없다.
- 정정: `0100`은 `origin/main`에 아직 없고 이 브랜치의 로컬 DB에만 적용됐다. `0101`을 따로 둔 것은 이미 적용한 파일은 고치지 않는다는 실행기 규칙을 지키기 위해서다.
