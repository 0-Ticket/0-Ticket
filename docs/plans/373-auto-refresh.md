# 대시보드 데이터 자동 갱신(polling) 추가

`286-auth-screens.md`에서 대체하는 것은 "서버가 요청마다 `last_seen_at`을 갱신하므로 주기 호출을 하지 않는다"는 이유 문장뿐이다. `me`를 주기적으로 부르지 않는다는 결론은 그대로다.

## 목표

화면을 연 채로 두면 10초마다 값이 조용히 바뀐다. 갱신 때 로딩 표시, 깜빡임, 스크롤·펼침·선택·필터·커서 페이지·탭의 초기화가 없고, 자동 갱신은 세션 유휴 만료를 늘리지 않는다. 마지막 갱신 시각이 화면에 보인다.

## 방법

### 서버: 자동 요청은 유휴를 늘리지 않는다

- 프런트는 자동 갱신 GET에 헤더 `X-Auto-Refresh: 1`을 붙인다. 서버(`session_user`)는 GET이고 이 헤더가 있을 때만 자동 요청으로 본다. 그 밖의 메서드에서는 헤더를 무시한다.
- `store.find_session_user`에 `touch: bool = True`를 더한다. `touch=False`이면 `UPDATE ... SET last_seen_at`을 하지 않고 같은 조건(활성 사용자, 절대 만료, 유휴 만료)으로 읽기만 한다. 사용자·권한 조회, `must_change_password` 검사는 그대로다. 헤더를 위조해도 자기 세션을 연장하지 못할 뿐이라 보안 영향은 없다.
- 자동 요청도 인증용 쓰기 연결을 연다(`docs/notes/284-auth-roles.md`). 읽기 연결로 바꾸는 것은 하지 않는다.

### 프런트: 갱신 훅과 공유 쿼리 옵션

- 간격은 `frontend/src/constants.ts`의 상수 한 곳(10초). 설정·환경변수는 만들지 않는다.
- `client.get`에 선택 인자(자동 요청이면 헤더를 붙임)를 더한다. 기존 호출은 그대로다.
- 화면마다 인라인으로 쓰던 `queryKey`·`queryFn`을 공유 쿼리 옵션 함수로 뺀다(대시보드, 목록, 상세, Incident 상세). 같은 옵션을 일반 `useQuery`와 갱신 훅의 `client.fetchQuery({ ...옵션, staleTime: 0 })`가 함께 쓴다. TanStack은 `queryFn` 안에서 요청이 타이머 때문인지 알 수 없어서, 표시를 붙이려면 훅이 자동 조회를 직접 부른다.
- 갱신 훅(`useAutoRefresh`)은 `setTimeout`으로 다음 조회를 건다.
  - 성공하면 10초, 연속 실패하면 10→20→40→60초(최대)이고 성공하면 10초로 돌아온다.
  - 숨은 탭(`document.visibilityState`)에서는 타이머를 걸지 않고, 보이게 되면(`visibilitychange`) 즉시 한 번 조회한다. 재연결(`online`)도 즉시 한 번 조회한다. 둘 다 백오프 대기를 끊고 10초로 되돌린다. 모두 자동 요청이다.
  - 화면을 벗어나거나 `enabled`가 꺼지면 타이머와 이벤트 구독을 정리한다. 진행 중인 요청은 `signal`로 취소한다.
  - 오류 처리: 401은 지금처럼 쿼리 캐시 `onError`가 로그인 화면으로 바꾸므로 훅은 멈춘다. 403·404는 갱신을 멈추고 에러 화면의 "다시 시도"(사용자 요청)를 누르면 재개한다. 네트워크 오류·5xx·그 밖은 백오프하며 계속한다. 첫 로딩이 실패해 데이터가 없어도 백오프 갱신을 계속한다.
- 갱신 대상 쿼리에만 `refetchOnReconnect: false`를 둔다. 기본값이 켜져 있어 재연결 조회가 표시 없이 나가면 세션을 연장하기 때문이다. 전역 기본값(`query-client.ts`)은 바꾸지 않는다. `me`·정책·사용자 관리 쿼리는 그대로다.
- 첫 로딩과 사용자가 시작하는 조회(화면 이동, "다시 시도", "분석 상태 새로고침", 승인·반려 뒤 `invalidateQueries`)는 표시 없이 지금처럼 유휴를 늘린다.
- 갱신 범위: 대시보드(홈과 목록 위 집계 차트, 같은 `["dashboard"]` 쿼리), Alert·Event·Ticket·Incident·Case·Hunting 목록, 상세 패널, Incident 페이지. 제외: `ticketing-policy`, Ticket 정책 화면, 사용자 관리, `me`. 개발용 `?sample=` 응답은 갱신하지 않는다(훅 `enabled=false`).

### 오류 분기와 값 유지

- v5는 백그라운드 갱신이 실패해도 `data`를 두고 `error`만 켠다. `layout.tsx`, `list-view.tsx`, `detail-panel.tsx`, `incident/page.tsx`는 "데이터가 있고 오류가 네트워크 오류(`ApiError`가 아닌 `fetch` 예외)나 5xx이면 값을 유지하고, 그 밖의 오류와 데이터가 없는 경우는 지금처럼 에러 화면"으로 바꾼다. 분류는 함수 한 곳에 둔다.
- `list-view.tsx`의 이전·다음 버튼 비활성 조건에서 `query.isFetching`을 뺀다(10초마다 깜빡이지 않게). 키가 바뀌면 `isPending`이 켜지므로 같은 보호가 된다. 다음 버튼의 `!!query.error`도 같은 분류를 따른다.

### 마지막 갱신 시각

- 위치: 페이지 제목 줄 오른쪽(홈·목록), Incident 페이지는 `incident-nav` 줄 오른쪽.
- 값: 화면에서 갱신 중인 쿼리들의 마지막 성공 시각 중 가장 오래된 것. 갱신이 연속 실패 중이면 "갱신 실패 · 마지막 성공 HH:MM:SS"로 바꾼다. 시각은 텍스트로만 표시한다.
- `design/`에 이 표시의 프레임이 없어 현재 스타일에 맞춘다. PR에 "디자인 없음"으로 표시하고 사람이 전·후 스크린샷을 붙인다(D-075).

### 반려 창

- `ReviewActions`가 `status !== "awaiting_review"`이면 `null`을 돌려주던 것을 바꿔, 창(`RejectDialog`)과 입력한 사유가 상태와 관계없이 열려 있는 동안 유지되게 한다. 승인·반려 버튼 줄은 지금처럼 `awaiting_review`일 때만 보인다.
- 창을 연 순간의 `review_round`·`analysis_round`·상태를 기억한다. 이후 상태가 `awaiting_review`를 벗어났거나 두 값 중 하나라도 달라졌으면 "내용이 바뀌었어요" 안내를 띄우고 창을 닫을 때까지 유지한다.
  - 상태가 `awaiting_review`가 아니면: "현재 상태: …. 반려할 수 없어요." 안내와 함께 "반려하기"를 비활성으로 한다. 사유는 복사할 수 있게 남는다.
  - 상태가 다시 `awaiting_review`인데 두 값이 바뀌었으면: "분석·검토가 바뀌었어요. 사유를 확인하세요." 안내를 띄우고 버튼은 켠다.
- 창을 연 시점 이후의 변화만 본다.
- 409 안내(`review.isError`)를 `Header`(`ReviewActions` 밖)로 옮겨, 다시 조회한 결과로 상태가 바뀌어 버튼 줄이 사라져도 남게 한다. 새 요청을 시작하거나 닫으면 지운다.

### 관계 그래프

- 그래프 탭을 연 시점부터 노드 위치, 확대 비율, 화면 위치를 고정하고 새 노드만 더한다. 탭을 옮기면 확대·화면 위치는 지금처럼 초기화되고, 노드 위치는 `useGraphMemory`로 남는다.
- 처음 그릴 때(`layout()` 결과 전체)와 새 노드가 생길 때마다 그 자리를 기억(`remember`)한다. 사용자가 조작하기 전에도 기존 노드가 밀리지 않는다. 새 노드는 기존 노드를 고정한 채로 `layout()`이 놓는다.
- 첫 그림에서 `vt`를 `fit(...)` 값으로 고정한다. "화면에 맞추기"는 `setVt(null)`이 아니라 지금 맞춤값을 저장한다. 보기(Ticket/Entity)를 바꾸면 그 보기의 첫 그림에서 다시 고정한다.
- 엔티티 보기는 연결 수 상위 60개(`ENTITY_CAP`)만 그린다. 순위가 바뀌어 노드가 빠지거나 들어오는 것은 허용한다. 자리는 `memory`에 남아 다시 나타나면 같은 자리다.

### 요청 수와 응답 시간(PR에 기록)

- 요청 수는 테스트의 `requests`로 센다. 1분당 홈 6, 목록 12(상세 패널을 열면 18), Incident 페이지 6이어야 한다.
- 응답 시간은 로컬 `docker compose` + 데모 데이터로 `/api/dashboard`와 상세 API를 `curl -w %{time_total}`로 20회 재 중앙값·p95를 적는다. 측정 때의 데이터 건수도 함께 적는다. 세션 쿠키는 어디에도 남기지 않는다. 측정 스크립트는 저장소에 넣지 않는다.

## 다른 코드와 맞물리는 곳

- 새 요청 헤더 `X-Auto-Refresh: 1`(GET 전용). 헤더가 없는 요청은 그대로 동작한다. `contracts/`와 응답 형식은 바뀌지 않는다.
- `store.find_session_user(conn, token, idle, touch=True)`: 기본값이 있어 기존 호출은 그대로다. 호출처는 `api/auth.py` 한 곳이다.
- `client.get`의 선택 인자: 기존 호출은 그대로다.
- 화면이 쓰던 쿼리 키(`["dashboard"]`, `["list", path]`, `["detail", resource, id]`, `["detail", "incidents", id, sample]`)는 바꾸지 않는다.
- `ReviewActions`의 `status`·`onApproved` 인자는 그대로고, 안내용 값(`review_round`, `analysis_round`)을 더 받는다. 호출처는 Incident 페이지 `Header` 한 곳이다.
- 인증(D-020, #284) 변경이다. 담당자 확인이 필요한지는 사람이 정한다.

## 범위 밖

- 서버가 변경을 밀어 주는 방식(SSE). 지연이나 서버 부하가 문제가 되면 후속 이슈로 분리한다.
- 갱신 간격의 화면·설정 변경과 환경변수.
- `ticketing-policy`, Ticket 정책 화면, 사용자 관리, `me`의 갱신.
- 자동 요청에서 쓰기 연결을 읽기 연결로 바꾸는 것.
- 사용자 입력(캐시로만 처리되는 클릭)으로 유휴를 늘리는 것.
- 1쪽 목록에 새 행이 들어올 때 클릭 위치가 밀리는 문제(알려진 한계).
- 마지막 갱신 시각 표시의 디자인 프레임.

## 완료 기준

- [ ] 대시보드를 열어 둔 채 새 건이 생기면 새로고침 없이 10초 안에 값이 바뀐다(목록, 상세 패널, Incident 페이지도 같다)
- [ ] 갱신 중에 스크롤 위치, 선택·펼침 상태, 필터, 커서 페이지, 탭이 유지되고 첫 로딩 말고는 로딩 표시와 버튼 깜빡임이 없는 테스트가 있다
- [ ] 숨은 탭에서는 요청이 나가지 않고, 보이게 되면 즉시 한 번 갱신되는 테스트가 있다. 재연결(`online`)도 즉시 한 번 갱신된다
- [ ] 연속 실패 때 간격이 10→20→40→60초로 늘고 성공하면 10초로 돌아오며, 실패하는 동안 마지막 성공 값이 유지되는 테스트가 있다
- [ ] 화면을 벗어나면(언마운트, `enabled` 꺼짐) 요청이 더 나가지 않는 테스트가 있다
- [ ] 오류 분기 테스트: 네트워크 오류·5xx는 값 유지, 401은 로그인 화면, 403·404는 에러 화면과 갱신 중지(다시 시도 뒤 재개), 첫 로딩 실패는 백오프 갱신으로 복구된다
- [ ] 타이머·탭 복귀·재연결 요청에만 `X-Auto-Refresh: 1`이 붙고, 첫 로딩·화면 이동·"다시 시도"·"분석 상태 새로고침"·승인·반려 뒤 재조회에는 붙지 않는 테스트가 있다. 갱신 대상 쿼리의 `refetchOnReconnect`가 꺼져 있다
- [ ] 백엔드 테스트: 표시 있는 GET은 `last_seen_at`을 갱신하지 않고(59분 상태 유지), 61분이면 401이며, 절대 만료·비활성 사용자·권한·`must_change_password` 검사는 같다. 표시 없는 GET과 표시 있는 POST는 지금처럼 갱신한다
- [ ] `?sample=` 응답과 `me`·정책·사용자 관리 쿼리는 갱신되지 않는 테스트가 있다
- [ ] 반려 창 테스트: 열려 있는 동안 갱신해도 창과 입력 사유가 유지된다. 갱신 사이에 `analyzing`으로 갔다 돌아온 경우, 상태는 그대로이고 `analysis_round`만 오른 경우(재분석 완료), `review_round`만 오른 경우에 안내가 뜨고, 아무것도 안 바뀌면 안내가 없다. `awaiting_review`가 아니면 "반려하기"가 비활성이다. 409 안내가 다시 조회한 뒤에도 남는다
- [ ] 관계 그래프 테스트: 갱신으로 노드가 늘어도 기존 노드 위치, 확대 비율, 화면 위치가 그대로이고 새 노드만 더해진다
- [ ] 마지막 갱신 시각이 제목 줄(Incident 페이지는 `incident-nav` 줄)에 보이고, 실패 중에는 실패 문구가 보이는 테스트가 있다
- [ ] 화면별 요청 수(1분당 홈 6, 목록 12, 목록+상세 18, Incident 6)를 테스트로 확인하고, `/api/dashboard`·상세 API 응답 시간(중앙값, p95)과 측정 때 데이터 건수를 PR에 적었다
- [ ] `uv run ruff format --check .`, `uv run ruff check .`, `uv run pytest`와 `frontend/`의 `pnpm contracts:check`, `pnpm lint`, `pnpm test`, `pnpm build`가 통과한다. 디자인이 바뀐 PR이라 사람이 전·후 스크린샷을 붙인다(D-075)
- [ ] `docs/decisions.md`(D-083), `docs/security.md`, 주석(`auth.py`, `session.ts`)이 맞고 `docs/notes/373-auto-refresh.md`가 있다

## 토론으로 정한 것

이슈 본문과 달라진 점:

- 이슈는 "프런트만"이었으나 자동 갱신이 세션 유휴 만료를 늘리지 않게 하려고 백엔드(`last_seen_at` 비갱신)까지 고친다. 이유: 10초 갱신이 유휴 만료를 무력화하기 때문이다.
- 갱신 범위를 대시보드에서 6개 목록, 상세 패널, Incident 페이지까지 넓혔다(이슈의 "정하지 못함"을 정함).
- 간격은 상수 한 곳 10초로 두고 설정·환경변수는 만들지 않는다.
- 갱신 중에도 반려 창과 사유를 유지하고, 관계 그래프의 상태를 고정한다.

사람이 정한 것(질문과 답):

1. 자동 요청 표시: `X-Auto-Refresh: 1` 헤더, GET만 인정(안 A). 쿼리 문자열은 URL·캐시 키·접속 로그를 건드려서 쓰지 않는다.
2. 갱신 장치: 훅이 타이머와 `fetchQuery`를 직접 쥔다(안 A). `refetchInterval`은 요청에 표시를 붙일 수 없다.
3. 마지막 갱신 시각: 제목 줄 오른쪽(Incident 페이지는 `incident-nav` 줄 오른쪽), 가장 오래된 성공 시각, 실패 중에는 실패 문구(안 A).
4. 반려 창: `awaiting_review`가 아니면 "반려하기" 비활성 + 현재 상태 안내, 409 안내는 `Header`로(안 A). 이어서 사람이 추가한 것: 창을 연 뒤 `review_round`가 바뀌면 다시 `awaiting_review`여도 안내하고, 갱신 사이에 재분석이 끝난 경우도 테스트한다. 같은 이유로 `analysis_round`도 함께 본다(안내용 값으로, 응답에 이미 있다).
5. 응답 시간 측정: 로컬 `docker compose` + 데모 데이터로 `curl` 20회, 중앙값·p95, 측정 때 데이터 건수를 PR에 적는다(안 A).
6. 오류 종류별 동작: 네트워크 오류·5xx·그 밖은 백오프하며 계속, 403·404는 갱신 중지(다시 시도로 재개), 401은 로그인 화면, 첫 로딩 실패도 백오프 갱신을 계속한다.
7. 엔티티 보기 상위 60개 변동은 허용한다.
8. 사람이 추가한 것: `refetchOnReconnect` 기본값이 켜져 있어 재연결 조회가 표시 없이 나가 세션을 연장하므로, 갱신 대상에서 끄고 재연결 조회는 훅이 자동 요청으로 보낸다. 테스트를 넣는다.
9. "처음 그린 시점"은 그래프 탭을 연 시점으로 해석한다.

결정 목록: D-083(화면 자동 갱신), D-020 메모(자동 갱신 요청은 유휴 만료를 늘리지 않는다). 원칙 7은 간격이 환경마다 다른 값이 아니라는 해석으로 부딪히지 않는다고 본다.
