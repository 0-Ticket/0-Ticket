# L2 구현 범위 (초안)

상태: 검토용 초안 · 2026-10-29

현재 단계: **박스별 이슈 작성 및 soc-plan 입력 준비**. 아래 ‘이슈별 작업 명세’를 이슈 본문에 사용한다. 이 문서의 작성 요청을 신규 정책·계약 변경이나 구현 계획의 승인으로 간주하지 않는다. GitHub 이슈는 사람이 등록하고, 이슈 번호를 받은 뒤 soc-plan을 실행한다.

전체 구조와 박스별 완료 조건은 [architecture.md](architecture.md), 데이터 형식은 [data-contracts.md](data-contracts.md), 확정된 도구와 정책은 [decisions.md](decisions.md)가 기준이다. 이 문서는 L2 구현 범위와 순서, 통합 검증 기준을 정한다. 새 필드명이나 미정 정책을 확정하는 문서는 아니다.

## 목표와 흐름

**목표**: L1에서 승격된 Ticket을 Incident로 묶고, L2 분석 결과를 사람이 승인해 Case로 확정하는 전체 흐름을 구현한다.

```text
기존 L1 Ticket (status = l2_escalated)
  → 엔티티 분기 (25): 엔티티 추출 · 공용 엔티티 제거 · 기존 Incident 확인
       ├─ 없음 → 새 Incident (18) + SIEM MCP 과거 조회 (15)
       └─ 있음 → 기존 Incident에 Ticket 추가 (18)
  → L2 Agent (19)
       타임라인 재구성 · ATT&CK 매핑
       → 증거 요청 큐 (26) → 전문가의 반복 조사
            허용된 MCP 선택 → 조회 → 후보 선별 → 추적
            → 증거 부족 시 다른 MCP 조회 또는 다른 후보로 복귀
       → 영향 범위 · 원인 분석
       → 발견 정보를 Incident에 추가
  → Incident Artifact (20) + 탐지 룰 제안 (24) + 대응 방안
  → Slack 알림 → 사람 승인 · 확정 (21)
       ├─ 승인 → Case (22) → RDB + VDB
       └─ 반려 → 사유를 넣어 L2 재분석 (2회 반려 시 사람 처리)
```

정규화 이후 분기(25)에서 이미 Incident에 속한 엔티티의 새 Alert를 기존 Incident에 추가하는 경로도 포함한다. L3 승격 Ticket은 같은 L2 입구를 쓰되, L3 Agent 자체는 이번 범위에 넣지 않는다.

## 범위

| 구분 | 박스 · 항목 |
|---|---|
| 신규 구현 | 18 Incident, 19 L2 Agent, 20 Incident Artifact, 24 탐지 룰 제안, 21 사람 승인·확정, 22 Case |
| 기존 기능 확장 | 25 엔티티 추출·공용 엔티티 제거·Incident 분기와 L2 입구 |
| 기존 기능 확장 | 26 Incident 주체의 증거 요청·결과 연결·실패 처리 |
| 재사용·필요 부분 확장 | 5 Lookup, 8 VDB, 12 Agent Log, 14 Web 전문가, 15 SIEM MCP, 공통 LLM·저장소·설정·레지스트리 |
| 사용자 접점 | Incident·Artifact 조회, 승인·반려, Case와 대응 작업·교훈 조회 및 수정, 관련 룰 제안·Agent Log 조회, Slack 알림 |
| 연동 검증 | L1 승격 Ticket 소비, 기존 Incident에 들어오는 새 Alert, 샘플 L3 승격 Ticket |
| 범위 밖 | L1 판정 로직 재구현, L3 헌팅 Agent(23), Cloud 전문가(13), 새 SIEM 종류 추가 |
| 범위 밖 | 차단·격리 등 대응 실행, 탐지 룰 자동 배포 |

화면과 API의 상세 범위는 [frontend.md](frontend.md), [api-contracts.md](api-contracts.md)를 따르고, v2와 다른 항목은 구현 계획에서 함께 정리한다. 기존 L1의 Ticket 생성과 `l2_escalated` 판정을 재사용한다.

## 동작 규칙

### Incident 생성과 갱신

- 엔티티 분기 결과에 따라 새 Incident를 만들거나 기존 Incident에 연결한다. Incident·Artifact는 PostgreSQL에 저장한다.
- 새 Incident 생성 시 SIEM MCP로 같은 엔티티의 과거를 조회한다. 조회 범위·한도·매칭 기준은 설정과 확정된 정책을 따르며, 미정 값은 구현 전에 결정한다.
- 발견 정보는 항상 추가한다. 단순한 시각·요약 갱신만으로 자동 분석을 반복하지 않는다.
- Incident 생성 시 분석을 시작하고, 이후에는 새 엔티티 또는 새 증거 ID가 늘었을 때만 자동 재실행한다(D-039).
- 자동 재실행 한도는 설정으로 두고 초기값은 5다. 한도 이후에도 정보는 저장하며, 자동 재실행이 멈췄다는 표시를 남긴다. 사람 반려에 따른 재분석과 자동 재실행의 횟수 관리는 구분한다.

### L2 분석과 결과

- Incident, 소속 Ticket, 판정 근거와 반려 사유를 입력으로 받는다. 유사 Case는 VDB에서 조회한다.
- 타임라인·ATT&CK 매핑, 증거 요청, 영향 자산·IOC·추정 원인·대응 방안을 만든다. 모든 주장에 근거 ID를 연결하고 실제 존재 여부를 코드로 검증한다.
- 증거 요청은 기존 큐를 통해 처리한다. 실패하면 공통 재시도 정책(D-034)을 적용하고, 최종 실패 시 확보된 증거로 분석을 계속한다. Incident를 보류하지 않으며 실패 사실을 결과와 승인 화면에 표시한다.
- 최대 단계 수와 토큰 예산을 설정하고 모든 분석·도구 호출·판정을 Agent Log에 기록한다. LLM 실패·예산 소진 시 결과 처리 방식은 LLM 정책과 대조해 구현 계획에서 확정한다.
- Web 전문가의 기존 Ticket 중심 입력·결과와 Incident 요청의 연결 방식을 계약 및 큐 검증과 함께 정리한다.

### L2와 전문가의 역할 분담

이번 초안에서는 전문가가 조사 목적에 맞는 여러 MCP를 선택하며 증거를 추적하는 방식을 제안한다. 현재 구현된 기능이나 연구에서 검증된 MCP 조합으로 간주하지 않는다. 도구 허용 범위·큐와의 연결·결과 계약은 구현 전에 확정한다.

| 담당 | 역할 |
|---|---|
| L2 Agent | Incident 전체의 조사 질문과 범위를 정하고 전문가에게 요청한다. 반환된 근거를 종합해 타임라인·ATT&CK·원인·영향 범위와 Artifact를 작성한다 |
| 전문가 Agent | 질문에 필요한 허용 도구를 선택하고 조회·후보 선별·추적·복귀를 반복한다. 확인한 사실과 미확인 사항을 근거와 함께 반환한다 |
| MCP | 로그·자산 등 데이터를 읽기 전용으로 조회하는 통로다. MCP 자체를 공격 경로나 원인으로 취급하지 않는다 |
| 실행 코드 | 도구 허용 목록, 조회 조건·결과 검증, 중복 조회 방지, 예산·종료 조건, 기록을 관리한다 |
| 사람 | Artifact·탐지 룰·대응 제안을 검토해 승인하거나 사유를 붙여 반려한다 |

전문가가 MCP를 바꿀 때마다 L2가 재배정하도록 강제하지 않는다. 다만 전문가의 허용 범위를 벗어나는 조사는 필요한 데이터와 이유를 L2에 반환해 조정한다. 기존 Web 전문가는 그대로 재사용할 부분과 L2 조사용으로 확장할 부분을 구분하고, L1 호출의 동작을 유지한다.

### 전문가의 반복 조사

1. 요청받은 질문, 시작 엔티티, 시간 범위와 기존 증거를 확인한다.
2. 확인할 가설과 다음 조회 목적을 정하고, 등록된 읽기 전용 MCP 도구 중 적절한 것을 선택한다.
3. 사전 정의된 조회 템플릿이나 구조화된 도구 인자를 채운다. 실행 코드는 허용 조건과 조회 한도를 검증한다.
4. 결과에서 추적할 후보를 선별하고, 유력한 후보를 먼저 조사하되 다른 후보도 보존한다.
5. 현재 소스에서 필요한 사실을 확인할 수 없으면 다른 허용 MCP로 이동한다. 연결 키와 시간 범위, 전환 이유, 앞선 근거를 유지한다. 데이터가 없는 것과 조회가 실패한 것을 구분한다.
6. 경로가 막히면 조건을 조정하거나 남겨 둔 후보로 돌아간다. 같은 조건의 무의미한 조회를 반복하지 않는다.
7. 질문에 필요한 증거를 확보하거나, 후보가 소진되거나, 예산에 도달하면 종료하고 부분 결과도 반환한다.

초기 검증은 기존 Web MCP와 SIEM MCP의 도구를 함께 사용하는 범위에서 시작한다. 서로 다른 도구가 같은 원본 기록을 반환하면 독립된 증거 두 개로 세지 않는다. 호스트·인증·Cloud 전용 MCP의 신규 구축은 이번 범위에 자동으로 포함하지 않으며, 데이터와 도구가 없으면 관측 불가로 남긴다.

조사 중 유지하고 반환해야 할 정보는 다음과 같다. 구체적인 필드명과 저장 위치는 계약 변경 계획에서 정한다.

- 확인한 사실, 이를 지지하거나 반박하는 근거 ID와 출처
- 추적 중인 엔티티·행위의 관계, 조사한 후보와 남은 후보
- 미확인 가설, 누락 로그·조회 실패 등 조사 한계
- 다음 조회 목적, 도구 선택·전환 이유, 종료 이유와 사용 예산

### 원인·영향 범위·타임라인

- **원인 조사**: 관찰된 행위에서 이전 기록을 역추적해 침입 경로와 원인 후보를 확인한다. 최초로 찾은 로그가 곧 최초 침입점이라는 결론을 내리지 않는다.
- **영향 범위 조사**: 발견한 계정·파일·IP 등의 후속 사용과 관련 자산을 조회한다. 단순히 같은 IP가 등장한 자산과 실제 침해가 확인된 자산을 구분한다. 역추적만으로 영향 범위 조사가 완료됐다고 보지 않는다.
- **타임라인**: 코드는 로그의 실제 발생 시각과 근거 ID로 정렬·중복 제거하고, L2는 행위 간 관계와 ATT&CK 매핑을 해석한다. 초기 타임라인을 추가 조사 결과로 보완한다. 시간순 인접만으로 인과관계나 공격 성공을 확정하지 않는다.
- **Artifact**: 위 조사 결과를 사람이 검토할 수 있는 보고서 데이터로 저장한다. 확인된 사실·추정·미확인 사항을 구분한다. AI가 탐지 룰과 대응 방안을 제안하고 코드는 룰을 검증하며, 최종 승인은 사람이 한다.

### 연구 적용 후보와 검증 범위

아래는 연구 폴더의 조사 문서를 바탕으로 한 적용 후보다. 방법 전체의 도입이나 논문 성능의 재현을 완료 조건으로 삼지 않는다.

| 참고 자료 | 이번 범위에 반영할 방향 | 이번에 확정하지 않는 부분 |
|---|---|---|
| [SherAgent](../../soc-incident-response-research/01-research/papers/PAPER-004_SHERAGENT.md) | 조회·후보 선별·추적·복귀로 원인 조사 구조화 | 후보 개수 등 세부 수치, 여러 MCP를 사용하는 경우의 효과 |
| [HESP](../../soc-incident-response-research/01-research/papers/PAPER-003_HESP.md) | 가설·증거 현황 유지, 중복 방지, 코드 기반 예산·종료 통제 | 가설 확률표와 정보이득 계산의 전면 도입 |
| [Agentic Investigation](../../soc-incident-response-research/01-research/papers/PAPER-001_agentic-investigation-security-alerts.md) | 조사·요약·근거 충분성 확인을 단계로 분리 | 각 단계를 별도 Agent나 별도 모델로 만드는 구성 |
| [SIR-Bench / OUAT](../../soc-incident-response-research/01-research/papers/PAPER-002-OUAT.md) | 시작 Ticket에 없던 사실을 발견했는지 근거 기반 평가 | Cloud 공격 재연 환경·데이터 증강 파이프라인 도입 |

연구 메모의 v1 역할 배분보다 현재 architecture.md를 우선한다. OpenTriage·Vigil 실습에서 기록된 검토 실패의 승인 처리와 가짜 근거 ID 문제를 회귀 검증 사례로 참고한다. AI 검토가 실패했다고 사람 승인이나 분석 성공으로 대체하지 않는다.

### 룰 제안·사람 검토·Case

- 기존 SIEM 시나리오에 없는 패턴을 ATT&CK 기법별 템플릿으로 제안한다. 문법 검사, SIEM 쿼리 변환, 저장된 Event 기반 백테스트를 수행한다.
- 탐지 룰 제안과 대응 방안은 Artifact 검토에 포함한다. 별도 룰 승인 흐름을 만들지 않고, 승인된 룰은 반영 대상으로 표시한다. 자동 배포하지 않는다.
- 분석이 끝나 사람 승인이 필요할 때만 Slack으로 알린다(D-033). L1 이벤트는 알리지 않는다.
- `review_state`와 `review_round`를 검토 기회의 기준으로 사용한다. 승인·반려는 C15로 기록하며, 같은 검토 기회를 중복 처리하지 않는다.
- 첫 반려는 사유를 입력으로 재분석하고, 두 번째 반려는 `human_handling`으로 넘긴다. 증거 수집 실패와 자동 재실행 한도 도달 표시를 승인 화면에 보여 준다.
- 승인된 Incident·Artifact를 Case로 확정한다. Case는 RDB와 VDB에 저장하고 대응 작업의 담당자·마감·상태와 교훈을 관리한다.
- 로그 원문·LLM 출력·확장 필드는 화면과 알림에서 텍스트로만 표시한다.

## 25·18번: 엔티티 분기부터 Incident 저장까지

아래 신규 동작 정책은 검토용 제안이다. 코드·계약·결정 대장은 아직 변경하지 않았으며, 이슈 작성 전 필요한 정책을 확정한다.

### 책임과 전체 순서

- **25 엔티티 분기**: 입력 근거에서 매칭 엔티티를 만들고 설정된 정책으로 기존 Incident 후보를 평가한다. LLM은 사용하지 않는다.
- **18 Incident**: 분기 결정을 최신 DB 상태에서 다시 확인하고, 생성·연결·근거 추가·분석 예약을 함께 저장한다. 과거 조회와 갱신을 관리한다.
- **19 L2**: 저장된 Incident의 특정 데이터 버전을 분석한다. Incident 매칭 정책은 결정하지 않는다.

```text
승격 Ticket 또는 정규화된 새 Alert
 → 입력·기처리 여부 검사
 → 근거 기반 엔티티 수집 → 매칭 키 생성 → 공용 엔티티 제외
 → 상태·엔티티·시간으로 후보 조회 → 결정
 → 트랜잭션 안에서 후보 재확인
      새 Incident 생성 / 기존 Incident 연결 / 애매한 건 별도 생성
 → 구성원·엔티티·근거·분기 사유·후속 작업 함께 저장
 → 커밋
      신규: SIEM 과거 조회 → 성공 또는 최종 실패 기록 → 첫 분석 예약
      기존: 새 엔티티·근거가 증가한 경우 분석 예약
```

외부 SIEM 조회와 LLM 호출은 DB 트랜잭션 안에서 하지 않는다.

### 1. 입력과 엔티티

#### 입력 자격

- L1은 `status=l2_escalated`인 기존 C6 Ticket을 소비한다. origin은 유지한다.
- L3 Ticket도 동일한 서비스 입구를 사용하되, 실제 L3 발행 조건은 후속 계약에서 정한다. origin만으로 임의의 미완성 Ticket을 받지 않는다.
- Alert 입구는 기존 25번 중복 제거 이후 사용한다. 매칭 Incident가 없으면 기존 시나리오·L1 경로로 보낸다. Alert만으로 새 Incident를 만들지는 않는다.
- 입력 ID가 이미 연결됐으면 같은 결과를 반환한다. 재실행은 구성원 중복 추가가 아니다.

#### 수집과 매칭 키 (제안)

- Ticket의 entities와 연결 Alert의 C5 엔티티를 수집한다. Ticket에 없는 엔티티도 근거 Alert ID를 보존해 추가한다. 원본 로그 문자열을 새로 LLM 추출하지 않는다.
- 기존 `alert_entities()`의 순서·원본 값은 바꾸지 않는다. 별도 매칭 계층에서 IP 표준 표현, 호스트의 대소문자·끝점 정리 등을 처리한다. 사용자명은 기본적으로 대소문자를 유지한다. 계정 도메인·호스트 별칭을 근거 없이 합치지 않는다.
- 엔티티 값과 함께 출처 ID, 발생 시각, C5에서 확인 가능한 src/dst/host/user 역할을 보존한다. Ticket entities만으로 역할을 알 수 없으면 unknown으로 둔다.
- Lookup의 공용 자산 표시·설정 목록에 해당하는 엔티티는 **매칭에서만 제외**한다. 원본과 관찰 근거를 삭제하지 않는다. IP가 사설 대역이라는 이유만으로 공용 처리하지 않는다.
- Ticket 시간 범위는 연결 Alert의 실제 발생 시각 최소·최대로 계산한다. 처리 시각을 공격 발생 시각으로 대체하지 않는다. 사용 가능한 시각이 없으면 별도 생성하고 시간 미확인 사유를 남긴다.

### 2. Incident 매칭 정책 (제안)

첫 버전은 점수 기반 AI 판단보다 설명 가능한 규칙을 사용한다. 여러 규칙이 맞으면 모두 평가하고, DB 조회 순서로 하나를 고르지 않는다.

| 조건 | 처리 제안 |
|---|---|
| 후보 상태 | open·investigating만 자동 연결. 승인 완료·사람 처리 상태는 자동 연결에서 제외 |
| 시간 | 입력과 Incident의 관찰 시간 구간 사이 간격이 설정값 이내. 초기 제안 60분, 승인 필요 |
| 강한 일치 | 비공용 출발지 IP와 대상 자산이 함께 일치하거나, 자산 범위가 확인된 계정이 일치 |
| 약한 일치 | 역할 없는 IP 하나, 공용 엔티티, 대상 서버만 일치하는 경우 자동 연결하지 않음 |
| 후보 1개 | 해당 Incident에 연결하고 규칙·일치 엔티티·시간 조건 기록 |
| 후보 0개 | Ticket은 새 Incident 생성. Alert는 기존 L1 경로 유지 |
| 강한 후보 여러 개 | 자동 병합하지 않음. Ticket은 별도 Incident 생성 후 관련 후보·충돌 사유 표시. Alert는 기존 L1 경로 유지하며 충돌 기록 |
| 유효 엔티티 없음 | Ticket은 독립 Incident 생성, 자동 매칭 불가 표시. Alert는 기존 L1 경로 유지 |

단일 엔티티 일치만으로 연결하는 규칙은 조직 설정으로 추후 추가할 수 있지만 기본 제안에는 넣지 않는다. 목표는 서로 다른 공격을 하나로 합치는 오류를 줄이는 것이다. 하나의 서버를 향한 여러 공격이 같은 사고라는 보장은 없다.

매칭 대상 엔티티는 원본 Ticket·Alert에서 확인된 것과 전문가가 근거를 붙여 확인한 것으로 제한한다. 단순히 같은 조회 결과에 등장한 엔티티나 LLM의 미확인 가설은 자동 매칭 키로 승격하지 않는다. 조사로 찾은 과거 로그는 근거로 추가하며 자동 Ticket 생성·Incident 병합을 유발하지 않는다.

현재 아키텍처의 ‘같은 엔티티’보다 보수적인 구체화 제안이다. 이 정책을 채택하면 architecture.md의 25번과 규칙 설정·테스트를 함께 맞춘다.

### 3. DB에 저장할 내용과 일관성 (제안)

| 저장 개념 | 보존할 내용 |
|---|---|
| Incident 본체 | ID·상태·review_state, 관찰 시각, 중요도, 데이터 버전, 초기 과거 조회 상태, 재실행 횟수·한도 표시 |
| 입력 연결 | Incident와 Ticket/직접 연결 Alert, 유일한 입력 ID, 연결 시각·분기 사유 |
| 엔티티 관찰 | 원본 값·매칭 키·역할·출처, 공용 여부, 매칭 사용 가능 여부 |
| 근거 연결 | Alert·Event·기타 허용 근거 ID, 출처와 조회 요청, 동일 근거 중복 방지 |
| 분기 기록 | C21 및 필요한 추가 기록: 선택 Incident, 후보·규칙·충돌·매칭 불가 사유 |
| 후속 작업 | 과거 조회·분석 예약의 상태, 재시도, 처리 중 데이터 버전 |

C10 members가 현재 Ticket/hunt만 표현하므로 직접 Alert 연결은 계약 변경이 필요하다. C21에는 목적 Incident ID·복수 후보 정보를 담는 방식이 부족하다. 새 필드는 기존 계약에 임의로 끼워 넣지 않고 계약 이슈에서 정한다.

- 하나의 입력은 자동 처리상 하나의 Incident에만 연결한다. 입력 연결의 유일성은 DB 제약으로 보장한다.
- 생성·구성원 연결·근거 추가·버전 증가·후속 예약은 같은 트랜잭션으로 커밋한다. 커밋 후 프로세스가 죽어도 작업자는 저장된 예약을 읽어 이어간다.
- 초기 구현은 Incident 매칭·쓰기 작업자 하나로 직렬 처리한다. 후보 선택부터 저장까지 같은 DB 잠금 정책을 적용하며 단일 작업자라는 가정을 문서화한다. 다중 작업자 확장은 별도 검증 전 허용하지 않는다.
- 기존 Incident에 추가할 때 시각 범위를 확장하고 중요도를 재계산한다. 근거·엔티티 집합은 유일 키로 중복을 막는다.
- 실패한 트랜잭션은 전체 롤백한다. 입력이 처리 완료로 기록되지 않으므로 재처리할 수 있다.

### 4. 새 Incident의 과거 조회와 첫 분석 (제안)

1. Incident와 입력을 먼저 저장한다. 이 시점부터 UI에서 수집 중임을 확인할 수 있다.
2. 기존 증거 요청 큐(26)에 Incident 주체의 SIEM MCP 과거 조회를 넣는다. 신뢰할 수 있는 비공용 엔티티와 규칙의 시간 범위를 사용한다.
3. 조회 범위는 최초 관찰 시각 이전 설정 구간으로 제한한다. 초기 조회 기간·전체 건수·엔티티 수·대기 시간 상한은 별도 승인할 설정값이다. 매칭 시간창과 과거 조회 시간창은 다른 값이다.
4. 조회 결과는 기존 수집·정규화 검증 경계를 재사용해 참조 가능한 근거로 저장한다. SIEM의 외부 ID와 내부 근거 ID 연결도 보존한다. 정규화 불가·잘림·일부 실패를 숨기지 않는다.
5. 성공 또는 재시도 후 최종 실패·대기 상한 도달 시 첫 L2 분석을 예약한다. 실패해도 Incident는 보류하지 않는다(D-034). 첫 분석에 초기 수집 결과를 포함해 불필요한 즉시 재실행을 줄인다.
6. 뒤늦게 추가 결과가 도착하면 정보는 저장하고 새 엔티티·근거 증가 조건에 따라 후속 분석을 예약한다.

초기 조회는 조사 시작 자료를 확보하는 고정 절차다. 이후 전문가는 특정 가설에 필요한 조회를 선택한다. 두 단계에서 동일한 근거를 다시 찾아도 새 근거로 세지 않는다.

### 5. 갱신과 분석 실행 (제안)

- 처음 분석은 재실행 5회에 포함하지 않는다. 새 정보로 시작한 자동 후속 분석의 상한을 5회로 해석하는 제안이며 D-039의 상세 계수 규칙을 승인받는다.
- 새 엔티티·근거가 증가하면 데이터 버전을 올린다. 설명 수정·같은 근거 재조회·Ticket 연결만으로 후속 분석을 예약하지 않는다. 연결 Ticket의 기존 근거가 새로 들어왔다면 증가로 본다.
- 분석 중 여러 입력이 들어오면 다음 분석 예약 하나로 모은다. 진행 중 분석은 시작 버전을 유지하고, 완료 시 최신 버전과 비교해 후속 분석 필요 여부를 확인한다.
- 승인 대기 중 새 정보가 생기면 기존 검토 기회를 무효화하고 재분석한다. 오래된 화면의 승인은 버전·검토 회차 검사로 거부한다. 이때 자동 한도에 도달하면 최신 정보 미반영 경고를 표시하고, 오래된 Artifact를 최신 분석으로 승인시키지 않는다. 수동 처리 전환은 21번 계약에서 정한다.
- 승인 완료 Incident는 다시 열거나 기존 Case를 자동 수정하지 않는다. 관련 새 Ticket은 새 Incident에서 처리하고 이전 사고와의 관련성을 기록한다.
- 사람 반려 재분석, 전문가 내부 조회 반복, 장애 재시도는 Incident 자동 재실행 횟수와 분리한다.

### 6. 예시와 완료 기준

| 입력 상황 | 기대 결과 |
|---|---|
| 첫 승격 Ticket: 출발지 A → 서버 B | Incident I1 생성·DB 저장 → 과거 조회 → 첫 분석 |
| 10분 뒤 같은 A → B의 다른 Ticket | I1 연결, 새 근거가 있으면 후속 분석 예약 |
| 같은 B를 향한 다른 출발지 C | 대상 B만으로 합치지 않고 새 Incident 생성 |
| 같은 입력을 두 번 처리 | 같은 연결 결과, 구성원·근거·예약 중복 없음 |
| 같은 A → B가 매칭 시간창 밖에서 발생 | 새 Incident 생성 |
| 후보가 여러 개 또는 공용 엔티티만 존재 | 별도 생성·사유 표시, 임의 병합 없음 |
| SIEM 조회 실패·작업자 재시작 | 실패 표시 후 분석 진행·미완료 예약 복구 |
| 분석 중 새 근거가 연속 도착 | 데이터 보존, 후속 분석 예약 합침, 한도 준수 |
| 승인 대기 중 새 증거 도착 | 오래된 검토 거부, 최신 버전 분석 또는 미반영 상태 명시 |

단위 검증에는 가짜 저장소·도구를 사용하고, DB 통합 검증은 유일성·롤백·재시작·동시 입력의 중복 생성 방지를 확인한다. 기존 L1 분기·Ticket 판정 결과가 바뀌지 않는지도 검증한다.

### 검토 후 정할 항목

우선 검토할 정책은 **강한 매칭 기준, 매칭 시간창, 복수 후보·무엔티티 처리, 초기 과거 조회 상한, 승인 대기 중 갱신 처리**다. 제안 승인 후 25·18·26·21 및 계약 변경의 이슈 경계를 정한다. soc-plan은 이 동작과 계약을 입력으로 파일·인터페이스·마이그레이션·검증 계획을 구체화한다.

## 선행 결정 (미확정)

아래 두 건은 결정 대장에 행이 없다. 후보 비교는 검토용이고 확정은 사람이 한다(`prompts/decision-review.md`). 확정 전에는 해당 이슈의 구현을 시작하지 않는다.

### D-042 · 탐지 룰 형식과 문법 검사·쿼리 변환 도구 (박스 24, L2-07 선행)

D-011(Sigma 2.0 상관 규칙)은 Correlation(17) 폐기와 함께 폐기됐고, 그 뒤로 룰 형식·검사 도구 행이 없다. 반면 `contracts/rule_proposal.schema.json`에는 `sigma_rule`·`siem_query`·`syntax_ok`·`backtest`가 이미 있다. 즉 형식은 사실상 Sigma이고, 미정인 것은 **문법 검사·쿼리 변환 구현체**다.

| 기준 | A. pySigma 라이브러리 | B. sigma-cli | C. 직접 구현 |

| 24 완료 조건(문법 검사·변환) | 파싱·검증·백엔드 변환을 라이브러리로 제공 | A를 CLI로 감싼 것, 같은 기능 | 전부 자체 구현 |

## 통합 검증과 완료 기준

1. L1의 `l2_escalated` Ticket에서 새 Incident가 만들어지고, 같은 엔티티의 후속 Ticket·Alert가 기존 Incident에 연결된다.
2. 샘플 L3 승격 Ticket도 같은 L2 입구로 처리된다. 실제 L3 Agent는 필요하지 않다.
3. 과거 조회·추가 증거가 타임라인·ATT&CK·영향 범위·원인 분석에 반영되고, 잘못된 근거 ID는 거부된다.
4. 새 엔티티·증거가 없으면 자동 재실행하지 않는다. 정보가 늘면 재실행하고, 설정 한도에서는 표시를 남긴 채 정보 저장을 계속한다.
5. 증거 요청이 재시도 후 실패해도 분석 결과가 만들어지며, 승인 화면에 실패 사실이 보인다.
6. 룰 제안에 문법 검사·쿼리 변환·백테스트 결과가 붙고, 승인 전에는 반영 대상으로 처리하지 않는다.
7. 승인 필요 상태에서만 Slack 알림이 발생하고, 승인 시 Case가 RDB·VDB에 저장된다.
8. 반려 사유가 재분석 입력에 반영되고, 두 번 반려되면 사람 처리로 넘어간다. 같은 검토 회차의 중복 제출은 거부된다.
9. Case의 대응 작업과 교훈을 저장·조회하며, 유사 Case 검색이 가능하다.
10. LLM·도구 실패와 예산 소진을 검증하고 Agent Log에 기록한다. 기존 L1 흐름이 유지된다.
11. 계약 동기화·박스별 테스트·통합 테스트와 저장소의 필수 검사를 통과하고, tests/checklist.md의 해당 완료 조건을 충족한다.

### 조사 방식의 비교 검증

같은 입력·도구·예산 조건에서 단순 조회 방식과 반복 조사 방식을 비교한다. 성공 기준과 기대 근거는 실행 전에 사람이 검토한 샘플로 정하고, 결과를 본 뒤 유리하게 바꾸지 않는다.

| 시나리오 | 확인할 동작 |
|---|---|
| 한 도구로 충분한 경우 | 불필요한 MCP 전환 없이 근거를 확보한다 |
| 다른 MCP의 도구가 필요한 경우 | 조사 질문과 연결 근거를 유지해 다른 도구로 이동한다 |
| 첫 후보가 잘못된 경우 | 다른 후보로 복귀해 조사를 이어간다 |
| 로그 누락·빈 결과·도구 오류 | 각각을 구분하고, 원인이나 무영향을 지어내지 않는다 |
| 후속 행위가 다른 자산에 있는 경우 | 원인 추적과 별도로 영향 범위를 조사한다 |
| 후보 소진·예산 도달·반복 조회 | 명시된 이유로 종료하고 확인된 부분 결과를 보존한다 |
| 로그에 지시문이 섞인 경우 | 데이터를 명령으로 실행하거나 도구 권한을 확대하지 않는다 |

측정 항목은 시작 Ticket에 없던 사실의 발견 여부, 원인·영향 자산의 정확성, 근거 없는 주장, 근거 연결의 유효성, 조회 횟수·시간·토큰 비용이다. 성능 향상은 비교 결과를 얻은 뒤에만 주장한다. 전문가 내부의 조사 반복 예산과 Incident 자동 재실행 한도(초기 5회)는 별도로 검증한다.

시연 데이터는 기존 L1 데이터와 합성 샘플을 우선 재사용한다. 실제 승격 Ticket 수, 기대 Incident 묶음과 분석·룰 기대값은 시연 준비 과정에서 확인해 기록한다. 아직 측정하지 않은 실행 결과는 완료로 간주하지 않는다.
