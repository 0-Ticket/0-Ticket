# L2 구현 범위

상태: 구현 이슈 작성 전 범위 문서 · 2026-10-30

이 문서는 [연구 아키텍처 v2](https://github.com/0-Ticket/soc-incident-response-research/blob/main/04-architecture/architecture-v2.md)의 L2 흐름을 구현 범위로 옮긴다. 연구 아키텍처의 기본 흐름, 이 저장소에서 이미 확정한 후속 정책, 아직 승인되지 않은 제안을 구분한다.

구현할 때의 최종 기준은 다음과 같다.

- 전체 구조와 완료 조건: [architecture.md](architecture.md)
- 데이터 형식: [data-contracts.md](data-contracts.md)
- 확정된 정책과 도구: [decisions.md](decisions.md)
- 확장 지점: [extensibility.md](extensibility.md)
- 비밀·로그 원문·화면 표시: [security-policy.md](security-policy.md)

연구 아키텍처 v2는 구성요소에 박스 번호를 부여하지 않는다. 이 문서의 박스 번호는 코드·결정·이슈를 연결하기 위해 **이 저장소의 `docs/architecture.md`가 부여한 내부 식별자**다.

## 아키텍처 v2 기본 흐름

### 입력

L2는 다음 세 경로를 같은 Incident 처리 흐름으로 받는다.

- L1에서 에스컬레이션된 Ticket
- L3 헌팅 결과 Ticket
- 사전 처리에서 열린 Incident와 연결된 Alert

L3 Agent 자체 구현은 이 마일스톤의 범위가 아니다. L3 헌팅 결과 모양의 Ticket이 L2 입구로 들어오는지만 샘플로 검증한다.

### 처리 순서

```text
L1 에스컬레이션 Ticket 또는 L3 헌팅 결과 Ticket
  → 엔티티 추출
  → 공용 엔티티를 Incident 대조에서 제외
  → 열린 Incident 확인
       ├─ 없음 → 새 Incident 생성 → SIEM MCP로 같은 엔티티의 과거 조회
       └─ 있음 → 기존 Incident에 Ticket 추가

열린 Incident와 연결된 새 Alert
  → 기존 Incident에 Alert 추가

Incident 생성·갱신
  → 타임라인 재구성 및 ATT&CK 매핑
  → 증거 요청 큐 → 전문가 Agent + MCP
  → 영향 범위 및 원인 분석
  → Incident Artifact 작성
       ├─ 탐지 룰 제안
       └─ 대응 방안 제시
  → Human 검토
  → 승인·확정 → Case 저장
```

### 역할

| 구성요소 | 아키텍처 v2의 책임 |
|---|---|
| Incident 연결 | Ticket의 엔티티를 열린 Incident와 대조해 새 Incident를 만들거나 기존 Incident에 추가한다 |
| L2 Agent | 타임라인과 ATT&CK 매핑을 만들고, 증거를 종합해 영향 범위와 원인을 분석한다 |
| 전문가 Agent | 큐로 받은 요청을 읽고 허용된 MCP로 증거를 가져온다. 사건의 최종 판정은 하지 않는다 |
| Incident Artifact | 타임라인, 영향 범위, 원인, 탐지 룰 제안, 대응 방안을 사람이 검토할 수 있게 보존한다 |
| Human | Artifact의 탐지 룰 제안과 대응 방안을 검토하고 승인·확정한다 |
| Case | 승인·확정된 사고와 교훈을 보존하고 이후 헌팅의 입력으로 제공한다 |

전문가 Agent는 증거 수집 역할이다. 여러 MCP를 자율적으로 오가며 후보를 추적하는 반복 조사 방식은 아키텍처 v2의 확정 흐름에 포함하지 않는다.

### 저장소

| 데이터 | 저장소 |
|---|---|
| Alert, Event, Lookup | RDB |
| Ticket | RDB + VDB |
| Incident, Incident Artifact | RDB |
| Case | RDB + VDB |

VDB에는 Ticket과 Case만 저장한다. Incident와 Artifact는 VDB에 넣지 않는다. 이 프로젝트의 별도 로그 저장소로 OpenSearch를 두지 않는다.

| 흐름 | 내부 박스 |

| Incident 생성·갱신 | 18 |

| 탐지 룰 제안 | 24 |

폐기된 박스 번호와 상세 코드 위치는 `docs/architecture.md`만 기준으로 한다. 이 문서에서 별도의 번호 체계를 만들지 않는다.

## 아키텍처 v2 이후 확정된 저장소 정책

다음은 연구 아키텍처 v2의 기본 흐름을 바꾸려는 제안이 아니라, `docs/decisions.md`에서 이미 확정한 실행 정책이다.

### Ticket 출처와 L2 입구

- Ticket 출처는 L1 승격, L3 승격, 시나리오로 구분한다(D-038).
- L1 승격·시나리오 Ticket은 L1 판정을 거친 뒤 L2로 들어간다.
- L3 승격 Ticket은 L1 판정을 다시 거치지 않고 L2 입구로 바로 들어간다.
- 직접 연결된 Alert는 새 Ticket을 만들지 않고 기존 Incident에 추가한다.

### 증거 요청 실패

- 증거 요청은 PostgreSQL 테이블 큐를 사용하고 설정된 횟수만큼 재시도한다(D-034).
- L2 요청이 최종 실패해도 Incident를 보류하지 않는다.
- 확보한 증거만으로 분석을 계속하고, 결과와 승인 단계에 `증거 수집 실패`를 표시한다.

### L2 재실행

- 발견한 정보는 재실행 한도와 관계없이 Incident에 항상 추가한다(D-039).
- 자동 재실행은 새 엔티티나 새 증거 ID가 늘었을 때만 한다.
- 최대 자동 재실행 횟수는 설정 값이고 초기값은 5다.
- 한도에 도달하면 정보는 계속 저장하고 자동 재실행만 멈추며 그 상태를 표시한다.
- 사람 반려에 따른 재분석과 증거 요청 재시도는 자동 재실행 횟수와 구분한다.

### 검토와 알림

- 사람이 승인하는 단계는 L2 결과의 승인·확정뿐이다.
- 반려하면 반려 사유를 넣어 L2가 다시 분석하고, 두 번째 반려 뒤에는 사람이 직접 처리한다(D-039).
- Slack 알림은 L2 분석이 끝나 승인이 필요할 때만 보낸다(D-033).
- Slack과 화면에서 로그 원문, LLM 출력, 확장 필드를 HTML이나 마크다운으로 렌더링하지 않는다(D-040).

### SIEM 연결

- 외부에 구축된 SIEM 하나를 설정으로 골라 연결한다(D-037).
- 새 Incident의 과거 조회는 선택된 SIEM의 읽기 전용 SIEM MCP를 사용한다(D-035).
- SIEM 종류가 바뀌어도 L2 코어 흐름은 바뀌지 않는다.

## 승인되지 않은 제안

다음 내용은 연구 아키텍처 v2나 결정 대장에서 확정되지 않았다. 구현 이슈의 완료 기준으로 사용하려면 별도 정책 검토와 사람 승인이 필요하다.

### 강한 Incident 매칭

- 출발지 IP와 대상 자산의 동시 일치 같은 `강한 일치` 규칙
- 고정된 Incident 매칭 시간창
- 강한 후보가 여러 개인 경우 별도 Incident 생성
- 공용 엔티티만 있는 Ticket을 독립 Incident로 만드는 처리

연구 아키텍처 v2는 공용 엔티티를 제외한 뒤 열린 Incident의 엔티티와 대조한다고만 정한다. 구체적인 강도·시간창·충돌 규칙은 확정된 분기 규칙에만 둔다.

### 전문가 반복·다중 MCP 조사

- 전문가가 여러 MCP를 스스로 선택하고 전환하는 방식
- 후보 선별·추적·복귀 상태의 장기 보존
- 가설별 조사 예산과 종료 조건
- 단순 증거 요청 방식과 반복 조사 방식의 성능 비교를 구현 완료 조건으로 삼는 것

전문가는 현재처럼 큐의 구조화된 요청을 받아 허용된 도구로 증거를 수집한다. 반복 조사 방식을 도입하려면 입력·출력 계약, 도구 허용 범위, 큐 재진입과 교착 방지, 평가 기준을 먼저 승인받는다.

### 미정 실행 값

- Incident 매칭 시간창과 강한 일치 기준
- 최초 SIEM 과거 조회의 기간·건수·엔티티 상한
- L2 조사 단계·시간·토큰 예산의 구체 값

확정되지 않은 값은 코드·기본 설정·계약에 임의로 넣지 않는다.

## 구현 범위

### 포함

- L1 승격 Ticket과 샘플 L3 승격 Ticket의 L2 입구
- 열린 Incident와 연결된 새 Alert의 기존 Incident 추가
- 새 Incident 생성과 SIEM 과거 조회
- 기존 Incident 갱신
- 타임라인·ATT&CK 매핑, 증거 요청, 영향 범위·원인 분석
- Incident Artifact, 탐지 룰 제안, 대응 방안
- 승인·반려와 Case 생성
- 증거 실패·재실행 한도·승인 필요 알림 표시
- Incident·Artifact·Case 조회와 승인에 필요한 기존 화면·API 연결

### 제외

- L1 승격·판정 로직 재구현
- L3 헌팅 Agent 구현
- Cloud 전문가 구현
- 새 SIEM 종류 추가
- 차단·격리·계정 잠금 같은 대응 실행
- 탐지 룰 자동 배포
- 승인되지 않은 강한 매칭 정책과 전문가 반복·다중 MCP 조사

## 구현 순서

1. 기존 계약의 v2 불일치와 L2 입출력 객체를 확인한다. 계약 변경이 필요하면 별도 계약 이슈와 승인 계획을 먼저 만든다.
2. Ticket·Alert의 L2 입구와 Incident 생성·갱신·과거 조회를 구현한다.
3. Incident 증거 요청과 실패 결과 연결을 구현한다.
4. L2 분석과 Incident Artifact 저장을 구현한다.
5. 탐지 룰 제안과 대응 방안을 Artifact에 연결한다.
6. 승인·반려, Slack 알림, Case 생성을 연결한다.
7. 화면·API와 전체 흐름을 통합 검증한다.

앞 단계가 아직 없으면 `tests/fixtures/`의 작은 손작성 계약 객체와 가짜 구현체로 다음 단계를 독립 검증한다. 계약 변경과 소비 코드를 나눠 병합하면 호환성을 보장할 수 없는 경우에만 승인된 작업 그룹으로 묶는다.

## 통합 완료 기준

1. L1 승격 Ticket에서 새 Incident가 만들어지고 같은 엔티티의 후속 Ticket이 기존 Incident에 추가된다.
2. 샘플 L3 승격 Ticket이 같은 L2 입구로 처리된다.
3. 열린 Incident와 연결된 새 Alert가 Ticket을 새로 만들지 않고 기존 Incident에 추가된다.
4. 새 Incident에서 SIEM 과거 조회 결과가 타임라인과 분석에 반영된다.
5. 타임라인·ATT&CK·영향 범위·원인과 모든 근거 ID가 검증된 Incident Artifact가 만들어진다.
6. 증거 요청이 최종 실패해도 확보한 증거로 분석이 계속되고 실패 상태가 승인 단계에 보인다.
7. 새 엔티티·증거가 없으면 자동 재실행하지 않고, 정보가 늘면 설정 한도 안에서 재실행한다.
8. 탐지 룰 제안과 대응 방안이 Artifact 검토에 포함되고 승인 전에 자동 반영·배포되지 않는다.
9. 승인 필요 상태에서만 Slack 알림이 발생하고, 승인 시 Case가 RDB와 VDB에 저장된다.
10. 반려 사유가 재분석 입력에 반영되고 두 번째 반려 뒤에는 사람 처리로 넘어간다.
11. 기존 L1 흐름과 계약·결정 대장의 의미가 바뀌지 않는다.
12. 저장소의 필수 포맷·린트·테스트와 관련 체크리스트 검증을 통과한다.
