# 결정 목록

팀이 정한 도구와 방식이다. "확정"인 것만 코드에 들어간다. 이 목록은 2026-11-03, PR #191부터 쓴다. 번호가 #191보다 작은 이슈·PR에 적힌 결정 번호는 이 목록과 관계없다.

## 상태

| 상태 | 뜻 |
|---|---|
| 확정 | 팀이 정했다. 코드에 쓴다 |
| 후보 | 유력하지만 팀이 아직 의논하지 않았다. 쓰려면 계획 이슈에서 확정한다 |
| 담당자가 정함 | 그 부분을 구현하는 담당자가 계획 이슈에서 정한다. 예시는 참고용이다 |
| 추후 | 지금은 만들지 않는다 |
| 폐기 | 쓰지 않기로 했다 |

## 쓰는 법

- 정할 것이 생기면 계획 이슈의 "어떻게"에 적는다. `/soc-plan`이 확정되지 않은 도구나 방식을 발견하면 안건으로 올린다.
- 사람이 정하면 이 문서의 해당 행을 "확정"으로 옮기고 맨 아래 "기록"에 한 줄을 남긴다. 상태는 사람만 정하고, 사람이 정한 것을 AI가 받아 적는 것은 괜찮다.
- 결정을 바꾸면 같은 ID의 내용을 고치고 기록에 남긴다. 번호는 다시 쓰지 않는다.
- 다른 문서에서 결정을 가리킬 때는 `PostgreSQL(D-012)`처럼 설명을 먼저 쓰고 괄호에 ID를 쓴다. ID만 쓰지 않는다.

### L2

| ID | 결정 | 메모 |
|---|---|---|
| D-027 | Incident 분류 방법. 규칙으로 후보 Incident를 추리고 최종 선택만 에이전트가 한다. 엔티티는 강한 신호(`file_hash`, `process`, `url`, `domain`, `user`)·보조 신호(`ip`, `host`)·공용 세 등급으로 나누고, 공용 엔티티도 지우지 않고 등급만 낮춰 보존한다. 후보 조회 경로는 설정으로 고르고 기본은 벡터 검색이다. 벡터 검색은 비슷한 Ticket이 속한 Incident를 모으고, 컬렉션이 없거나 조회가 실패하거나 PostgreSQL에서 상태·`Incident.updated_at` 시간 창 확인을 통과한 유효 후보가 없으면 열린 Incident 직접 조회로 떨어진다. 어느 경로든 Ticket과 겹치는 신호를 세서 고른다. 분류 전용 에이전트는 두지 않고 같은 에이전트에 분류용 프롬프트를 덮어쓴다(에이전트 구조, D-024). 에이전트가 실패하거나 후보에 없는 Incident를 고르면 강한 신호가 가장 많이 겹치는 후보에 붙이고, 그런 후보가 없으면 새 Incident를 만든다. 보류하지 않는다. 저장은 고른 Incident 한 줄을 잠그고 아직 열려 있는지 다시 본 뒤 한 트랜잭션으로 한다 | 공용 엔티티를 지우면 잘못 묶인 Incident가 조사 단계에서 저절로 복구된다는 근거가 없어 보존한다. 보류하지 않는 이유는 Ticket이 어디에도 붙지 못하는 쪽이 더 나쁘고, 분류는 판정이 아니라 묶기라 결정적인 대안이 있기 때문이다. 확신도는 분류 출력에 담아 Agent Log에 남기되 판정에는 쓰지 않는다. 임계로 거를지는 기록이 쌓인 뒤 정한다. 저장 때 상태를 다시 보는 것은 에이전트가 도는 동안 사람이 그 Incident를 승인·종결할 수 있기 때문이다. 분류는 단계별 스레드(D-024)라 한 번에 하나씩 돌아 Ticket끼리의 경쟁은 없다. `origin = l3` Ticket은 Alert가 없을 수 있어 `hunt_id`로 Hunt를 읽는다(Hunt 계약, #217). 분류 출력도 `contracts/`에 계약으로 넣어야 한다(`AgentTask.output_contract`는 등록된 계약 이름만 받는다). 신호 등급 목록·시간 창·후보 수는 설정 값이다. 시간 창은 PostgreSQL에서 Incident에 한 번 적용하고 벡터 쪽 Ticket 시각으로는 거르지 않는다. 벡터 검색은 참 후보를 놓치거나 무관한 후보를 낼 수 있고 최종 선택은 에이전트가 한다. 잘못 연결된 Ticket을 자동으로 떼거나 재배정하는 기능은 없어 같은 공격의 상관관계가 나뉜 채 남을 수 있다 |
| D-028 | L2 재분석 기준. 재분석은 외부에서 새 Ticket이 Incident에 붙었을 때와 사람이 반려했을 때만 한다. L2 조사 중에 찾은 근거와 엔티티는 Incident에 붙이고 그 라운드 판정에 쓰되 재분석 신호로 삼지 않는다. `analysis_round`가 한도(기본 5)에 이르면 멈추고 멈춘 사실을 분석 결과에 남긴다. `review_round`가 한도(기본 2)에 이르면 `human_handling`으로 넘긴다 | 조사 → 근거 추가 → 갱신 → 재분석 → 다시 조사의 무한 루프를 막기 위해서다. 한도 값은 설정이다. 한도에 걸려 멈춘 Incident에도 Ticket은 계속 붙인다 |
