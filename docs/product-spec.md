# 제품 정의

## 한 줄 정의

SIEM 알럿을 AI 에이전트가 판정하고, 관련 알럿을 사고 단위로 묶어 보고서까지 만들고, 알럿이 없는 위협은 헌팅으로 찾아 탐지 룰을 제안한다. SOC 분석가는 검토와 승인만 한다.

## 사용자

| 사용자 | 지금 겪는 문제 | 0-Ticket이 해 주는 것 |
|---|---|---|
| L1 분석가 | 알럿이 너무 많고 대부분 오탐이다. 같은 판정을 반복한다. | 알럿마다 판정과 근거를 미리 만든다. 확신이 낮은 것만 사람에게 넘긴다. |
| L2 분석가 | 흩어진 알럿을 손으로 엮어 공격 흐름을 만든다. | 관련 티켓을 사고(Incident)로 묶고 타임라인 보고서를 만든다. 승인된 사고는 Case로 대응을 관리한다. |
| 탐지 엔지니어 | 탐지 시나리오가 없는 위협은 알럿조차 없다. | 헌팅 결과로 새 탐지 룰을 제안하고, 백테스트 결과와 함께 검토받는다. |
| 운영자 | SIEM마다 연동을 새로 만들어야 하고, 회사 환경에 맞게 고치려면 코드를 뜯어야 한다. | 기존 SIEM은 어댑터로 붙이고, SIEM이 없으면 새로 구축한다. 로그 소스, 자산 정보, 저장소, LLM, 규칙을 설정과 플러그인으로 바꾼다. |

## 사용자 시나리오

### S1 · 웹 알럿 단건 판정

1. 외부 IP `203.0.113.10`이 웹서버 `web-01`에 SQL 인젝션을 시도해 SIEM 알럿이 생긴다.
2. 알럿이 정규화되고, `web-01`이 중요도 5 자산이라는 정보가 붙는다.
3. L1 에이전트가 비슷한 과거 종결 티켓을 참고하고, 필요하면 Web Agent에 공격 성공 여부를 묻는다.
4. L1이 판정(TP / FP / 불명), 확신도, 근거 ID, 권고 조치를 낸다.
5. 확신도가 낮거나 자산 중요도가 높으면 분석가에게 넘어간다. 분석가는 동의하거나, 이유를 적고 판정을 뒤집는다.
6. 에이전트가 무엇을 조회하고 어떻게 판단했는지 Agent Log에서 확인할 수 있다.

### S2 · 캠페인으로 묶고 보고서 승인

1. 같은 출발지에서 스캔 → SQL 인젝션 → 웹셸 업로드 시도 알럿이 차례로 들어온다.
2. 각 알럿이 S1처럼 판정된다.
3. TP로 판정되거나 사람이 TP로 확정한 티켓들이 Correlation에서 같은 출발지·같은 목적지·1시간 이내 같은 규칙으로 Incident 하나로 묶이고, 묶인 이유가 남는다.
4. L2 에이전트가 관계없는 티켓을 빼고(이유와 함께), 빠진 단계를 로그 조회로 채워 타임라인 보고서를 만든다.
5. 분석가가 보고서를 승인하면 Case가 생기고 대응 작업을 관리한다. 반려하면 사유와 함께 L2가 다시 분석한다.

### S3 · 클라우드 알럿 판정

1. 클라우드 감사 로깅이 중지됐다는 알럿이 들어온다.
2. L1이 Cloud Agent에 묻고, Cloud Agent가 같은 주체의 앞뒤 1시간 API 호출을 분석해 결과를 돌려준다.
3. 이후는 S1과 같다.

### S4 · 위협 헌팅과 룰 제안

1. L3 에이전트가 최근 Case와 ATT&CK 기법을 바탕으로 헌팅 가설을 세운다.
2. 이벤트에서 통계 기준선(드문 프로세스, 처음 보는 국가 로그인 등)으로 범위를 좁힌다.
3. 좁혀진 결과를 LLM이 해석해 이상 징후를 찾으면 Correlation으로 넘겨 관련 티켓과 함께 Incident로 묶는다.
4. 헌팅 결과나 Case에서 기존 SIEM에 없는 반복 패턴을 찾으면 Sigma 룰을 제안하고, 문법 검사와 백테스트 결과를 붙인다.
5. 탐지 엔지니어가 검토해 승인한 룰만 SIEM에 반영된다.

### S5 · 회사 환경에 맞추기

1. 운영자가 회사에서 쓰는 SIEM 어댑터를 설치하거나, 없으면 기본 SIEM을 구축한다.
2. 사내 CMDB를 룩업 제공자로 연결하고, 자산의 부서·비용 센터 같은 추가 속성을 `extensions`로 붙인다.
3. 사내 LLM의 주소와 모델 이름을 설정에 적고, L2 에이전트만 더 큰 모델을 쓰게 한다.
4. 회사 룰 체계에 맞는 라우팅 규칙과 Correlation 규칙 파일을 추가한다.
5. 이 모든 것을 코어 코드 수정 없이 조직 설정 파일과 플러그인 패키지로 한다.

## 사용자 접점

- 알럿 넣기: 연결된 SIEM에서 자동으로 들어온다. 개발과 테스트에는 샘플 재생 도구를 쓴다.
- 검토하기: L1 티켓에 동의 / 뒤집기(이유 필수), L2 보고서 승인 / 반려(사유 필수), 룰 제안 승인 / 반려
- 결과 보기: 티켓 판정, Agent Log, Incident 보고서, Case 진행 상황, 룰 제안과 백테스트 결과

화면은 웹이다(결정 대장 D-013). 화면 목록과 규칙은 `docs/frontend.md`, 화면이 부르는 API는 `docs/api-contracts.md`에 있다. 검토 입력의 검증은 화면이 아니라 코어가 하므로, 메신저 같은 다른 채널을 검토 채널 플러그인으로 붙여도 같은 규칙이 적용된다.

## 범위 밖

- 사람 승인 없이 차단·격리·계정 잠금 같은 대응 동작을 실행하는 기능
- 사용자 계정, 권한 관리, 다중 조직 지원
- 악성코드 실행·동적 분석
- 모델 학습, 파인튜닝
- 실제 기업 로그와 자산 정보를 레포에 두는 것 (실행 환경에서 연결해 쓴다)
