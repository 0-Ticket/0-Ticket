# 제품 정의

## 한 줄 정의

SIEM 알럿을 AI 에이전트가 판정하고, 관련 티켓을 같은 엔티티의 사고(Incident)로 묶어 보고서·대응 방안·탐지 룰 제안까지 만들고, 알럿이 없는 위협은 헌팅으로 찾는다. SOC 분석가는 L1 결과를 조회하고, L2 결과를 승인·확정만 한다.

## 사용자

| 사용자 | 지금 겪는 문제 | 0-Ticket이 해 주는 것 |
|---|---|---|
| L1 분석가 | 알럿이 너무 많고 대부분 오탐이다. 같은 판정을 반복한다. | 정규화부터 L1 판정까지 완전 자동이다. L1 Agent가 알럿마다 증거를 모아 판정하고, 종결·보류하거나 L2로 올린다. 분석가는 어떤 알럿이 승격·보류됐는지 조회만 한다(읽기 전용). |
| L2 분석가 | 흩어진 알럿을 손으로 엮어 공격 흐름을 만든다. | 같은 엔티티의 티켓을 Incident로 묶고 타임라인, 영향 범위, 원인, 대응 방안, 탐지 룰 제안을 만든다. 분석가는 승인·확정만 하고, 확정된 사고는 Case로 대응을 관리한다. |
| 탐지 엔지니어 | 탐지 시나리오가 없는 위협은 알럿조차 없다. | L3 헌팅으로 알럿 없는 위협을 찾고, L2가 Incident에서 새 탐지 룰을 제안한다. 룰은 L2 승인·확정에 포함해 검토한다. |
| 운영자 | SIEM마다 연동을 새로 만들어야 하고, 회사 환경에 맞게 고치려면 코드를 뜯어야 한다. | SIEM(Wazuh 기준), 로그 소스, 자산 정보, 저장소, LLM, 규칙, 알림을 설정과 플러그인으로 바꾼다. 위협 시나리오를 입력해 헌팅을 시킨다. |

## 사용자 시나리오

### S1 · 웹 알럿 판정 (L1)

1. 외부 IP `203.0.113.10`이 웹서버 `web-01`에 SQL 인젝션을 시도해 Wazuh 알럿이 생긴다.
2. 알럿이 OCSF로 정규화되고, `web-01`이 중요도 5 자산이라는 정보가 붙는다.
3. 엔티티 분기(25)가 중복을 빼고 엔티티를 추출해 공용 엔티티를 지운다. 열린 Incident에 없는 엔티티다.
   - 공격 대상 시나리오면 Ticket이 바로 만들어진다.
   - 그 외 시나리오면 L1 Agent가 엔티티 정보를 조회해 승격(Ticket 생성)하거나 보류(L3 헌팅 데이터 풀)한다.
4. Ticket은 증거 요청 큐를 거쳐 Web 전문가 Agent가 MCP로 공격 성공 여부를 분석한다.
5. L1 Agent가 판정한다. 오탐은 확신도가 높으면 종결, 낮으면 보류한다. 이상 행위는 종결하거나 L2로 승격한다. 임계값과 갈림 조건은 미정(D-036). 판정하지 못하는 건도 사람에게 넘기지 않는다.
6. 분석가는 L1 결과 조회 화면에서 승격·보류·판정 결과를 본다. 판정을 뒤집거나 승격을 막지 않는다.
7. 에이전트가 무엇을 조회하고 어떻게 판단했는지 Agent Log에서 확인할 수 있다.

### S2 · Incident로 묶고 승인 · 확정 (L2)

1. 같은 출발지에서 스캔 → SQL 인젝션 → 웹셸 업로드 시도 알럿이 차례로 들어오고, S1처럼 L2로 승격된다.
2. 첫 Ticket의 엔티티로 열린 Incident가 없으므로 새 Incident가 생기고, SIEM MCP로 같은 엔티티의 과거를 조회해 넣는다.
3. 다음 Ticket은 같은 엔티티의 기존 Incident에 추가된다. 0단계에서 이미 Incident에 있는 엔티티의 알럿도 기존 Incident에 추가된다.
4. Incident가 생기거나 갱신될 때마다 L2 Agent가 타임라인을 재구성하고 ATT&CK에 매핑하며, 증거를 요청해 영향 범위와 원인을 분석한다. 기존 엔티티의 추가 정보를 찾으면 Incident에 더하고 다시 분석한다.
5. 결과는 Incident Artifact로 저장되고 탐지 룰 제안과 대응 방안이 함께 붙는다.
6. 분석가가 승인·확정하면 Case가 생기고 대응 작업을 관리한다.

### S3 · 클라우드 알럿 판정 (보류)

Cloud 소스(D-005)가 보류라 이 시나리오도 보류한다. 구조는 S1과 같고, Cloud 전문가 Agent만 다르다.

### S4 · 위협 헌팅 (L3)

1. 운영자가 위협 시나리오를 입력한다. L3 Agent는 이것과 최근 Case, L1이 보류한 건을 바탕으로 가설을 세운다.
2. Event·Alert(RDB)와 SIEM MCP로 가설을 검증한다. 통계 기준선으로 먼저 좁히고, 좁혀진 결과만 LLM이 해석한다.
3. 가설이 기각되면 기록만 남긴다. 위협이 있으면 헌팅 결과 Ticket을 만들어 L2로 넣고, 이후는 S2와 같다.

### S5 · 회사 환경에 맞추기

1. 운영자가 회사에서 쓰는 SIEM 어댑터를 설치한다. 기본은 Wazuh다.
2. 사내 CMDB를 룩업 제공자로 연결하고, 자산의 부서·비용 센터 같은 추가 속성을 `extensions`로 붙인다.
3. 사내 LLM의 주소와 모델 이름을 설정에 적고, L2 에이전트만 더 큰 모델을 쓰게 한다.
4. 회사 룰 체계에 맞는 공격 대상 시나리오 목록과 엔티티 분기 규칙 파일을 추가한다.
5. 이 모든 것을 코어 코드 수정 없이 조직 설정 파일과 플러그인 패키지로 한다.

## 사용자 접점

- 알럿 넣기: 연결된 SIEM에서 자동으로 들어온다. 개발과 테스트에는 샘플 재생 도구를 쓴다.
- 승인하기: L2 Incident Artifact(대응 방안, 탐지 룰 제안 포함)를 승인·확정해 Case로 만든다. 사람의 승인은 여기에만 있다.
- 헌팅 시키기: 운영자가 위협 시나리오를 입력한다.
- 결과 보기: L1 결과(승격·보류·판정, 읽기 전용), 티켓 판정, Agent Log, Incident 보고서, Case 진행 상황, 헌팅 결과, 룰 제안과 백테스트 결과
- 알림 받기: Slack(D-033). 트리거 이벤트는 미정.

화면은 웹이다(D-013). 화면 목록과 규칙은 `docs/frontend.md`, 화면이 부르는 API는 `docs/api-contracts.md`에 있다. 검토 입력의 검증은 화면이 아니라 코어가 하므로, 다른 채널을 검토 채널 플러그인으로 붙여도 같은 규칙이 적용된다.

## 범위 밖

- 사람 승인 없이 차단·격리·계정 잠금 같은 대응 동작을 실행하는 기능
- 사용자 계정, 권한 관리, 다중 조직 지원
- 악성코드 실행·동적 분석
- 모델 학습, 파인튜닝
- 실제 기업 로그와 자산 정보를 레포에 두는 것 (실행 환경에서 연결해 쓴다)
