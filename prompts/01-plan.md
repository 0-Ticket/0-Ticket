# 1단계: 계획

이 단계에서는 코드나 파일을 고치지 않는다. 계획만 세우고 사람의 승인을 기다린다.

## 입력

- 이슈 번호. 없으면 먼저 묻는다.

## 절차

1. `gh issue view <번호>`로 이슈를 읽는다. "무엇을 / 왜 / 완료 기준"을 확인한다.
2. `AGENTS.md`의 "먼저 읽을 문서" 순서대로 읽는다. `docs/architecture.md`는 "구현 순서"와 관련 박스의 절만 읽는다. 앞 단계 박스가 아직 없으면 그 출력은 샘플 객체로 대신한다고 계획에 적는다.
3. `docs/data-contracts.md`에서 이 박스가 받는 객체와 내보내는 객체를 찾는다.
4. `docs/decisions.md`에서 필요한 결정이 "확정"인지 확인한다.
5. `tests/checklist.md`에서 이 박스에 해당하는 항목을 찾는다.
6. LLM을 부르는 박스라면 `docs/llm-policy.md`를 읽는다.
7. 화면 작업이면 `docs/frontend.md`에서 그 화면(F 번호)의 경로, 쓰는 계약, 표시 규칙, 검토 동작을 찾고, `docs/api-contracts.md`에서 그 화면이 부르는 API를 찾는다. `docs/frontend.md` "명령" 표가 비어 있으면(F0 전) 화면 코드 계획을 세우지 않고 멈춘다.
8. 기존 코드가 있으면 앞뒤 박스 코드를 확인한다.

## 출력 (아래 형식 그대로)

```
대상: 이슈 #<번호> · 박스 <번호> <이름>  (화면 작업이면: 화면 F<번호> <이름>)

데이터 계약
- 입력: C<n> <객체명>
- 출력: C<n> <객체명>
- 계약 변경: 없음 / <필드, 이유>  (있으면 승인 필요)

바꿀 파일 (순서대로)
1. <경로>: <무엇을>

새로 만들 샘플 (tests/fixtures/, 화면은 mock 데이터)
- <파일>: <어떤 내용>

화면 (화면 작업일 때만)
- 경로: <경로>
- 부르는 API: <메서드 경로>
- 검토 동작: 없음 / <동작, 필수 입력>
- 텍스트로만 표시할 값: <필드>

검증 방법
- <테스트 이름>: <무엇을 확인>
- 체크리스트: K<n>, K<n>

필요한 결정
- D-xxx <항목>: 확정 / 미확정
  (미확정이 있으면 여기서 멈춘다)

확장 지점 (docs/extensibility.md)
- 없음 / <확장 지점>: 인터페이스 <경로>, 기본 구현체 <이름>, 새 설정 값 <키>

새 라이브러리
- 없음 / <이름>: <이유>

질문
- <애매한 점>
```

## 멈출 때

- 필요한 결정이 "확정"이 아니면 계획에 그렇게 적고 구현으로 넘어가지 않는다. `prompts/decision-review.md`로 검토를 제안한다.
- 이슈가 박스 두 개 이상에 걸치면 이슈를 나누자고 제안한다.
- 데이터 계약을 바꿔야 하면 바꿀 내용을 제안하고 승인을 기다린다.
