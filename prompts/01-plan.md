# 1단계: 계획

이 단계에서는 코드나 파일을 고치지 않는다. 계획만 세우고 사람의 승인을 기다린다.

## 입력

- 시작 이슈 번호 하나. 없으면 먼저 묻는다. 계약 변경 그룹이면 이슈 본문의 `함께 반영할 이슈` 항목을 따라 그룹 후보를 찾아 통합 계획에 열거한다. 사용자가 여러 번호를 줬다면 그 이슈들도 함께 확인한다.

## 절차

1. `gh issue view <번호>`로 시작 이슈를 읽고 "무엇을 / 왜 / 완료 기준"을 확인한다. 그룹 후보는 다음 순서로 확인한다.
   - `함께 반영할 이슈` 항목의 조정 이슈와 `Refs #<번호>`에 적힌 이슈를 읽는다. 새로 확인한 이슈의 같은 항목도 확인하되, 이미 읽은 이슈를 반복 조회하지 않는다. 다른 항목의 참고 링크나 `Refs`, 템플릿 주석의 예시만으로 그룹에 포함하지 않는다.
   - 그룹 후보가 있으면 각 이슈의 번호와 이 항목의 `Refs`를 합친 목록에 순서와 관계없이 같은 이슈들이 포함되는지 확인한다. 조정 이슈도 동일하며 그 목록에 포함돼야 한다. 각 이슈의 범위와 완료 기준도 기록한다. 연결 형식은 `CONTRIBUTING.md`의 "그룹 이슈 연결"을 따른다.
   - 그룹 후보 간 연결이 누락되거나 불일치하면 이슈별 문제와 GitHub 본문에 붙여 넣을 수정 문구를 출력한다. 사람의 의도가 불명확하면 조정 이슈·그룹 목록을 확인하고, 사람이 본문을 수정한 뒤 모든 그룹 후보 이슈를 다시 조회한다. 연결이 일치하기 전에는 그룹을 확정하거나 구현하지 않는다. 조회에 실패한 이슈는 그룹에서 임의로 빼지 않고 실패를 알린다.
   - 여러 박스에 걸치면 박스별 이슈를, 계약 변경이 있으면 계약 이슈를 확인한다. 필요한 이슈가 빠져 있으면 사람이 만들도록 요청한다. 그룹 항목이 없거나 `해당 없음`이어도 영향 분석에서 함께 반영할 변경이 발견되면 그룹과 연결 보완을 제안한다. AI는 GitHub 이슈를 생성하거나 수정하지 않는다.
2. 데모 준비 중에는 그룹의 모든 박스에 대해 `docs/milestone-demo.md` 범위를 확인한다. 범위 밖 박스가 있으면 해당 이슈와 이유를 알리고 계획을 멈춘다.
3. `AGENTS.md`의 "먼저 읽을 문서" 순서대로 읽는다. `docs/architecture.md`는 "구현 순서"와 그룹의 각 박스 절을 읽는다. 앞 단계 박스가 아직 없으면 그 출력은 샘플 객체로 대신한다고 계획에 적는다.
4. `docs/data-contracts.md`에서 영향받는 모든 박스의 입출력 객체를 찾는다. 맨 위 "v2 불일치"에 걸리는 객체면 계약 변경 제안을 계획에 넣는다. 그룹은 같은 계약을 쓴다는 이유만으로 만들지 않고, 필수 변경을 나누면 승인된 계약의 완료 기준이나 호환성을 안전하게 만족할 수 없는 경우로 한정한다. 독립 PR로 안전하게 완료할 수 있는 후속 작업은 그룹에서 뺀다. 분석 결과 이슈의 그룹 링크를 바꿔야 하면 1번의 수정·재조회 절차를 거친 뒤 그룹을 확정한다.
5. `docs/decisions.md`에서 필요한 결정이 "확정"인지 확인한다.
6. `tests/checklist.md`에서 그룹의 각 박스에 해당하는 항목을 찾는다.
7. LLM을 부르는 박스라면 `docs/llm-policy.md`를 읽는다.
8. 화면 작업이면 `frontend/AGENTS.md`를 읽고, `docs/frontend.md`에서 그 화면(F 번호)의 경로, 쓰는 계약, 표시 규칙, 검토 동작을 찾고, `docs/api-contracts.md`에서 그 화면이 부르는 API를 찾는다. F0(프론트 기반)은 `docs/frontend.md` "명령" 표의 스크립트를 만드는 작업이므로 그대로 계획한다. F1 이후 화면은 F0이 끝났는지(`frontend/package.json`에 "명령" 표의 스크립트가 모두 있는지) 확인하고, 끝나지 않았으면 화면 코드 계획을 세우지 않고 멈춘다.
9. 기존 코드가 있으면 그룹의 모든 영향받는 박스와 그 앞뒤 박스 코드를 확인한다.

## 출력 (아래 형식 그대로)

```
대상 및 작업 그룹
- 조정 이슈: #<사람이 지정한 번호> (여러 이슈의 계약 변경 그룹에만 필요; 단일 이슈면 해당 없음)
- 포함 이슈: #<번호>, #<번호> (단일 이슈면 그 이슈 하나)
- 이슈별 범위와 완료 기준: #<번호> — 공통 계약 / 박스 <번호> <이름> — <완료 기준>; ...
- 그룹 이유: <여러 이슈 그룹에만 해당: 같은 PR에서 완료해야 하는 계약·호환성 조건; 단일 이슈면 해당 없음>
- 그룹 담당자: <그룹 전체를 한 브랜치에서 구현·검증할 담당자 한 명, 사람이 지정> (단일 이슈면 해당 없음)
- 그룹 링크 확인: <해당 없음 / 모든 이슈의 그룹 목록·조정 이슈 일치 / 수정 필요: 이슈별 문제와 본문 수정 문구>
- 작업 브랜치: <type>/<이슈번호 또는 조정이슈번호>-<짧은설명>
- PR 제목: <type>(<scope>): <summary> (#<이슈번호 또는 조정이슈번호>)

데이터 계약
- 입력·출력: <각 영향받는 박스와 C<n> 객체>
- 계약 변경: 없음 / <필드, 의미, 타입, nullable·호환 규칙, 이유> (있으면 사람의 명시 승인 필요)

바꿀 파일 (순서대로)
1. <경로>: <무엇을>

새로 만들 샘플 (tests/fixtures/, 화면은 mock 데이터)
- <파일>: <어떤 내용>

화면 (영향받는 화면마다)
- 화면 F<n>: <경로>; API <메서드 경로>; 검토 동작 <없음 / 동작과 필수 입력>; 텍스트로만 표시할 값 <필드>

검증 방법
- <박스별 테스트>: <각 박스 계약의 입력·출력과 완료 기준 확인>
- <그룹 통합 테스트(그룹 작업에만 해당)>: <생산·저장·조회·소비 경계 및 기존 데이터 호환 확인>
- 계약을 바꿀 때: Schema와 생성 코드 동기화, 손작성 fixture의 `soc.contracts.validate_contract()` 검증
- 체크리스트: <영향받는 각 박스의 K 항목>

필요한 결정
- D-xxx <항목>: 확정 / 미확정
  (미확정이 있으면 여기서 멈춘다)

계약 제안 승인
- <필요 / 불필요>: <필드 의미·타입·호환 규칙과 작업 계획을 사람이 명시적으로 승인; 여러 이슈 그룹이면 그룹 전체 계획 포함>

확장 지점 (docs/extensibility.md)
- 없음 / <확장 지점>: 인터페이스 <경로>, 기본 구현체 <이름>, 새 설정 값 <키>

새 라이브러리
- 없음 / <이름>: <이유>

질문
- <애매한 점>
```

## 멈출 때

- 필요한 결정이 "확정"이 아니면 계획에 그렇게 적고 구현으로 넘어가지 않는다. `prompts/decision-review.md`로 검토를 제안한다.
- 이슈가 박스 두 개 이상에 걸치면 박스별 이슈로 나누도록 제안하고, 필요한 박스별 이슈가 등록되기 전에는 해당 다중 박스 작업의 구현을 시작하지 않는다. 데이터 계약도 바뀌면 계약 이슈를 추가한다. 계약 변경 그룹은 필요한 이슈가 모두 등록되고 그룹이 승인되기 전에는 구현하지 않는다.
- 그룹 후보 간 링크가 누락·불일치하면 그룹을 확정하거나 구현하지 않는다. 사람이 이슈 본문을 정리한 뒤 AI가 다시 조회해 확인한다. 필요한 이슈를 조회할 수 없어도 멈추고 사유를 알린다. 이슈에 링크가 있다는 사실만으로 그룹과 계약 변경이 승인된 것으로 보지 않는다.
- 데이터 계약을 바꿔야 하면 필드 제안과 작업 계획을 함께 제시한다. 여러 이슈 그룹이면 그룹 계획을 포함한다. 승인은 필드 제안과 작업 계획을 명시적으로 포함해야 한다. 그룹 구성, 조정 이슈, 담당자, 계약 의미, 박스 범위가 승인 뒤 바뀌면 계획을 갱신하고 다시 승인받는다.
- 여러 이슈의 계약 변경 그룹에서 조정 이슈나 그룹 담당자 한 명이 정해지지 않았으면 계획에서 선택을 요청한다. 사람이 지정하고 그룹을 승인하기 전에는 작업 브랜치를 만들거나 구현하지 않는다. 단일 이슈 작업에는 이 지정을 요구하지 않고 기본 작업 절차를 따른다.
