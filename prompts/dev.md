# 개발

확정된 계획대로 개발한다. 계획에 없는 일은 하지 않는다.

## 입력

- 이슈 번호. 작업 브랜치에 `docs/plans/<이슈번호>-*.md`가 없으면 개발하지 않고 `prompts/plan.md`부터 한다.

## 절차

1. 작업 브랜치로 옮기고 계획 파일을 읽는다. `gh issue view <번호> --comments`로 이슈를 다시 읽어, 확정 뒤에 바뀐 내용이 있으면 멈추고 묻는다.
2. 계획의 "바꿀 곳"과 그 앞뒤 코드, 같은 곳을 다룬 `docs/notes/` 기록을 읽는다.
3. `docs/notes/_template.md`로 `docs/notes/<계획 파일과 같은 이름>.md`를 만든다. 개발하면서 알게 된 함정, 임시 처리, 고른 것을 그때그때 적는다.
4. `tests/fixtures/`에 손으로 만든 작은 샘플을 만든다(`docs/security.md` "데이터").
5. 테스트를 먼저 쓰고 지금은 실패하는지 확인한다.
6. 테스트가 통과하도록 구현한다.
7. 의미 있는 단위로 로컬에 커밋한다. 메시지 첫 줄은 `<type>(<scope>): <summary> (#<이슈번호>)`.

## 지킬 것

- 키, 토큰, 비밀번호는 환경변수로만 읽고, 새 환경변수는 `.env.example`에 이름만 추가한다.
- 에이전트·LLM 호출은 테스트에서 가짜 응답으로 대신한다. 실제 호출 테스트는 `llm` 마커로 나눠 기본 실행에서 뺀다.
- DB·Qdrant가 필요한 테스트는 `db`·`qdrant` 마커로 나눈다. 그 마커를 처음 쓰는 이슈는 `.github/workflows/ci.yml`에 서비스 컨테이너와 `uv run pytest -m db`(또는 `-m qdrant`) 단계를 추가한다. 그러지 않으면 CI가 그 테스트를 돌리지 않고 통과한다.
- 밖에서 온 문자열은 `docs/security.md` "밖에서 온 문자열"대로 다룬다.
- 새 라이브러리는 `docs/decisions.md`에 확정된 것만 쓴다. 그 밖의 라이브러리가 필요하면 멈추고 묻는다.

## 계획과 달라져야 하면

- 목표, 범위, 다른 코드와 맞물리는 곳, 완료 기준이 달라지면 멈추고 무엇이 왜 다른지 말한다. 사람이 정하면 계획 파일 "바뀐 점"에 날짜와 한 줄을 추가하고 계속한다.
- 파일 나누는 방식이나 함수 이름처럼 작은 것은 기록의 "계획과 달라진 점"에 적고 계속한다.

## 출력

- 브랜치 이름과 커밋 목록
- 바꾼 파일과 각각의 이유
- 계획과 달라진 점 (없으면 "없음")
- 기록에 적어 둔 것 요약
