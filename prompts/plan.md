# 계획: 검토 → 토론 → 확정

사람이 이슈에 쓴 계획을 검토하고, 사람과 토론해 확정한다. 확정 전에는 코드와 문서를 고치지 않는다.

## 입력

- 이슈 번호. 없으면 먼저 묻는다.

## 1. 읽기

1. `gh issue view <번호> --comments`로 이슈 본문과 댓글을 읽는다. "함께 반영할 이슈"에 적힌 이슈도 읽는다. 읽지 못하면 멈추고 알린다.
2. `docs/architecture.md`, `docs/decisions.md`, `docs/security.md`를 읽는다.
3. 이슈가 건드리는 코드 위치와 낱말로 `docs/plans/`와 `docs/notes/`를 찾아 최근 것부터 읽는다(`docs/notes/README.md` "찾는 법").
4. 바꿀 코드와 그 앞뒤(이 코드를 부르는 곳, 이 코드가 부르는 곳, 같은 데이터를 읽고 쓰는 곳)를 직접 읽는다.

## 2. 검토 결과 내기

파일을 고치지 않고 아래 형식으로 낸다. 문제가 없는 칸은 "없음"이라고 쓴다. 이슈를 그대로 받아쓰지 않는다. 사람의 계획이 틀렸다고 생각하면 이유와 함께 분명히 말한다.

```
## 이해한 계획
<이슈의 계획을 내 말로 3~5줄. 내가 잘못 이해했으면 여기서 바로 보이게>

## 충돌
- <원칙(docs/architecture.md), 확정된 결정, 보안 규칙, 기존 코드, 다른 계획·기록과 부딪히는 곳. 근거 파일과 함께>

## 잘못됐거나 확인이 필요한 것
- <사실과 다른 가정, 동작하지 않을 방법, 확정되지 않은 도구>

## 빈칸
- <정하지 않으면 개발할 수 없는 것. 데이터 형식, 실패했을 때 동작, 완료 기준을 확인할 방법 등>

## 질문
1. <질문> — 선택지: A <...> / B <...>. 추천: <A, 이유 한 줄>
2. ...
```

- 질문은 개발 방향을 바꾸는 것만 묻는다. 관례로 정해지는 사소한 것(변수 이름 등)은 묻지 않는다.
- 확정되지 않은 도구가 필요하면 질문에 넣고, 답이 나오면 `docs/decisions.md`에 넣을 줄을 함께 제안한다.

## 3. 토론

- 사람이 답하면 그 답이 다른 부분에 주는 영향을 다시 확인한다. 새 충돌이나 빈칸이 생기면 다시 묻는다.
- 사람의 답에 동의하지 않으면 이유를 말하고 다른 안을 낸다. 사람이 그래도 정하면 따르고, "토론으로 정한 것"에 남긴다.
- 매 응답 끝에 "지금까지 정해진 것"과 "남은 질문"을 짧게 정리한다.
- 남은 질문이 없으면 확정해도 되는지 묻는다. 확정은 사람이 "확정"이라고 말한 것이다.

## 4. 확정

사람이 확정하면:

1. `git fetch origin` 후 최신 `origin/main`에서 작업 브랜치를 만든다: `<type>/<이슈번호>-<짧은설명>`.
2. `docs/plans/_template.md` 형식으로 `docs/plans/<이슈번호>-<짧은설명>.md`를 쓴다. "토론으로 정한 것"에는 원래 이슈와 달라진 점과 그 이유만 적는다.
3. 토론에서 사람이 확정한 결정이 있으면 `docs/decisions.md`의 "확정"과 "기록"에 추가한다.
4. 로컬에 커밋한다: `docs(plans): add plan for <짧은 설명> (#<이슈번호>)`.
5. 이슈 댓글 초안을 출력한다. 댓글은 사람이 단다.

```
## 확정 계획 (<날짜>)

계획 파일: `docs/plans/<파일>` (브랜치 `<브랜치>`)

### 요약
<목표와 방법 3~5줄>

### 이슈 본문과 달라진 점
- <달라진 점과 이유>

### 완료 기준
- [ ] ...
```

## 하지 않을 것

- 확정 전에 코드나 문서를 고치거나 브랜치를 만들지 않는다.
- 이슈나 댓글을 직접 고치거나 달지 않는다.
- 사람이 정하지 않은 것을 정해진 것처럼 계획 파일에 쓰지 않는다.
