# 2단계: 구현

사람이 승인한 계획대로 구현한다. 계획에 없는 일은 하지 않는다.

## 입력

- 시작 이슈 번호와 승인된 계획. 계약 변경 그룹이면 승인된 통합 계획의 모든 이슈 번호와 그룹 담당자 한 명을 확인한다. 계획 승인이 없거나 그룹 전체·계약 제안 승인이 빠졌으면 1단계(`prompts/01-plan.md`)로 돌아간다.

## 절차

1. 구현 시작·재개 전 `gh issue view <번호>`로 시작 이슈와 승인 계획에 포함된 모든 이슈를 다시 읽는다. 조회에 실패하면 사유를 알리고 멈춘다.
   - `prompts/01-plan.md` 절차 1에 따라 최신 그룹 링크를 확인하고, 그룹 목록·조정 이슈·작업 범위·완료 기준을 승인 계획과 대조한다. 단일 이슈로 승인받았더라도 새 그룹 연결이 생겼으면 확인한다.
   - 그룹 후보 간 연결이 누락·불일치하면 구현을 멈추고, 필요한 본문 수정 문구를 출력해 사람이 수정한 뒤 다시 조회한다. 단일 이슈의 그룹 항목이 없거나 `해당 없음`인 것은 연결 누락으로 보지 않는다.
   - 그룹 구성·조정 이슈·담당자·계약 의미·박스 범위·완료 기준이 승인 내용과 달라졌으면 계획을 갱신하고 다시 승인받는다. 기존 승인만으로 바뀐 범위를 구현하지 않는다.
2. `git fetch origin` 후 승인된 계획에 따라 작업 브랜치를 준비한다. 처음 만드는 단일 이슈 브랜치는 최신 `origin/main`에서 `<type>/<이슈번호>-<짧은설명>`으로 만든다(예: `git switch -c feat/12-ocsf-alias origin/main`). 계약 변경 그룹은 같은 기준에서 `<type>/<조정이슈번호>-<짧은설명>`으로 만들고, 계획에 적힌 그룹 담당자 한 명이 이 브랜치에서 그룹 전체를 구현한다. 재개할 때는 계획에 적힌 기존 브랜치와 작업 내용을 확인하고 이어서 작업한다. type은 `AGENTS.md` "작업 흐름"을 따른다. fetch가 안 되거나 그룹의 조정 이슈·담당자가 정해지지 않았으면 멈추고 알린다.
3. 계약 변경이 승인됐다면 `docs/data-contracts.md` → `contracts/`의 Schema → 생성 명령 순서로 먼저 고친다. 생성된 파일은 직접 고치지 않는다.
4. 샘플을 먼저 만든다. `tests/fixtures/`에 손으로 만든 작은 데이터를 둔다. IP는 문서용 대역, 도메인은 `example.com`을 쓴다. 화면 작업이면 `docs/api-contracts.md` 응답 모양 그대로 mock 데이터를 만든다.
5. 테스트를 먼저 쓰고, 지금은 실패하는지 확인한다.
6. 테스트가 통과하도록 구현한다. 코드 위치는 `docs/architecture.md`의 "박스 그룹과 코드 위치" 표를 따른다. 화면은 `docs/frontend.md`의 "폴더"를 따르고, 계약 타입은 `frontend/src/contracts/`, API 호출은 `frontend/src/api/`에만 둔다.
7. 의미 있는 단위로 나눠 로컬에 커밋한다. 커밋 메시지 첫 줄은 `<type>(<scope>): <summary> (#이슈번호)`이다. 그룹 작업은 조정 이슈 번호를 쓴다. 예: `feat(box4): add OCSF alias table loader (#12)`, `test(box4): add alias table fixtures (#12)`

## 지킬 것

- `docs/data-contracts.md`의 필드명, 타입, 필수 여부를 그대로 쓴다.
- 키, 토큰, 비밀번호는 하드코딩하지 않고 환경변수로 읽는다. 새 환경변수가 생기면 `.env.example`에 이름만 추가한다.
- LLM을 부르는 코드는 `docs/llm-policy.md`를 따른다. 테스트는 가짜 응답으로 한다.
- 화면 코드는 `docs/frontend.md`와 `docs/security-policy.md` 7항을 따른다. 로그 원문, LLM 출력, `extensions` 값은 텍스트로만 표시하고, 등록형 값 목록을 화면 코드에 고정하지 않는다.
- 확장 지점은 `docs/extensibility.md`를 따른다. 인터페이스와 구현체를 나누고, 코어에서 구현체 이름으로 분기하지 않으며, 조직별 값은 설정으로 뺀다. 가짜 구현체로 교체하는 테스트를 함께 만든다.
- "확정"되지 않은 결정 항목의 도구나 데이터셋을 쓰지 않는다.
- 계획과 달라져야 하면 멈추고, 무엇이 왜 달라지는지 먼저 말한다.
- 커밋 메시지에 AI 표시를 넣지 않고, push하지 않는다.

## 출력

- 만든 브랜치 또는 이어서 작업한 브랜치 이름
- 계약 변경 그룹: 포함 이슈·조정 이슈·그룹 담당자, 최신 이슈 내용과 승인 계획의 대조 결과
- 변경한 파일과 각각의 이유
- 새로 넣은 라이브러리와 이유 (없으면 "없음")
- 계획과 달라진 점 (없으면 "없음")
